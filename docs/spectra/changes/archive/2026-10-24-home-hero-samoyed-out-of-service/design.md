## Context

首頁插圖是 `app/frontend/hero/scene.js` 的 three.js 場景，一圈 21 秒（`CYCLE`）。公車開進末站，前門打開，司機下車到車旁休息，再走回車上，車開到站牌載客後開走。第 5.5 秒（`STILL`）是定格畫面，`tools/hero` 的匯出頁在這一格匯出兩張 WebP，給沒有 JS、設定減少動態效果、沒有 WebGL 的人看。首頁的 `app/frontend/hero/runtime.js` 每一格都呼叫 `pose(parts, seconds)` 再畫，所以 `pose()` 管得到的東西會跟著動畫動。

現在跟這次有關的部分：

- `bus()` 在車頭擋風玻璃上方有一塊空白的路線牌：一個 0.04×0.28×1.9 的 slate-800 方塊，底在公車座標 (`front`, 2.74, 0)，`front` 是車長的一半加 0.01（6.01）。公車是通用車，沒有業者塗裝、路線號碼、機關標誌。
- `dispatchOffice()` 有桌子、排班板、「洋流」海報與站長；朝街的那面牆在調度室座標 z = 1.9，窗洞從 x −2.0 到 1.6、高 0.8 到 2.15，沒有玻璃，所以從鏡頭的角度隔著窗看得到調度室中間的地板。調度室整組放在世界座標 (−11.4, 0, 3.3)。
- 窄螢幕的鏡頭只在末站與站牌之間移動，調度室在框外。
- `runtime.js` 的 `start()` 建好場景之後，先在 `requestAnimationFrame` 之外同步畫第一格，three.js 在這一格編譯畫得到的材質；一開始畫不到的東西（隱藏的，或在鏡頭框外的），要到第一次被畫出來的那一格才編譯它的材質、上傳它的貼圖。
- 規格 `home-page` 的「Hero picture」寫了一圈的情節、定格畫面與靜態圖要相同，以及「不顯示時鐘、倒數或任何 figure」。

使用者的要求（2026-10-24）：司機下車休息時，公車的跑馬燈亮「暫停服務」，啟動準備載客時熄掉；調度室裡加一隻薩摩耶。先在畫布上看過示意圖，才決定怎麼做（見 Design Source）。同一輪也畫過人行道上的導盲磚，使用者看過之後決定不做。

## Goals / Non-Goals

**Goals:**

- 桌機的全景隔著調度室的窗看得到一隻坐著的薩摩耶，色票不加顏色。
- 司機下車休息的這段時間，車頭路線牌跑「暫停服務」；其餘時間跟現在一樣空白。定格畫面整句置中，兩張靜態圖跟著重新匯出。
- 規格寫清楚：動畫不顯示的是數字；路線牌何時亮、何時空白。
- 每格耗時與動畫 chunk 的大小照舊在預算內，路線牌第一次亮起來的那一格也一樣。

**Non-Goals:**

- 導盲磚（使用者看過示意圖後決定不做，2026-10-24）。國內的《市區道路及附屬工程設計規範》14.4 與《市區道路人行道路口導盲設施設計指南》都沒有公車站的條文；日本的《道路移動等円滑化基準》第 34 條有（據日本總務省 2014 年仙台公車站調查的資料引述，沒有讀省令原文）。
- 車身側面的跑馬燈或放大的路線牌：使用者看過實際大小後選了只亮車頭，接受桌機上讀不出字（2026-10-24）。
- 路線牌上的路線號碼或目的地、LED 點陣的字。
- 狗的動作；狗出現在手機畫面。
- 改一圈的時間軸（`TIMELINE`、`CYCLE`、`STILL`）、鏡頭，或場景裡其他的物件。
- 放寬每格 16 ms 的預算，或把第一次畫某種材質的那一格排除在預算外（使用者選了先編譯材質，2026-10-24）。

## Decisions

### 調度室裡加一隻坐著的薩摩耶，不會動

`scene.js` 新增 `samoyed()`，回傳一隻面向 +x、腳在原點的狗，由 `dispatchOffice()` 放在調度室座標 (−0.9, 0, 0.4)、`rotation.y` −0.5。牠不在 `parts` 裡，`pose()` 不碰牠，所以不會動。調度室在地塊裡面，不用切。

造型用場景現有的 `box()`、`ball()` 與一個四角錐（耳朵），尺寸照原型（世界單位；`box()` 與 `ball()` 的位置是底的位置，跟 `scene.js` 的慣例一樣）：

| 部位 | 形狀與尺寸 | 顏色 |
| --- | --- | --- |
| 後半身 | 球，半徑 0.21，底在 (−0.13, 0, 0) | slate-100 |
| 胸口 | 圓角方塊 0.26×0.42×0.34，圓角 0.13，底在 (0.03, 0.1, 0)，繞 z 轉 −0.3 | slate-100 |
| 頸毛 | 球，半徑 0.17，底在 (0.1, 0.32, 0) | slate-100 |
| 前腳 | 兩根圓角方塊 0.09×0.4×0.09，圓角 0.04，底在 (0.15, 0, ±0.08) | slate-100 |
| 尾巴 | 球，半徑 0.13，底在 (−0.33, 0.24, 0.1)，捲在背上 | slate-100 |
| 頭 | 一組，中心在 (0.16, 0.62, 0)：球，半徑 0.15，以中心為頭的原點 | slate-100 |
| 嘴 | 頭的座標裡，圓角方塊 0.15×0.1×0.13，圓角 0.05，底在 (0.11, −0.1, 0) | slate-100 |
| 鼻子 | 頭的座標裡，球，半徑 0.03，底在 (0.185, −0.075, 0) | slate-800 |
| 眼睛 | 頭的座標裡，兩顆球，半徑 0.022，底在 (0.124, 0.003, ±0.071) | slate-800 |
| 耳朵 | 頭的座標裡，兩個四角錐（`ConeGeometry(0.055, 0.13, 4)`），中心在 (−0.02, 0.167, ±0.08)，轉 (±0.3, π/4, 0) | slate-100 |

一共 13 個 mesh（照上表數的：身體 6 個、頭 7 個）。頭頂到耳尖約 0.85 高；人約 1.62 高，比例接近真的薩摩耶坐著的高度。

位置的理由：坐著的狗頭頂約 0.85，要整隻從窗洞看得到，牠離朝街那面牆不能太近（窗台 0.8 高的實牆會擋住），也不能太遠（窗上緣 2.15 以上的牆會擋住頭）。原型在 (−0.9, 0, 0.4) 整隻都在窗洞裡，不擋站長、桌子與排班板（調度室特寫看過）。

理由：使用者要求，看過示意圖後選坐著（2026-10-24）。毛色沿用 slate-100：牠背後是 slate-300 的地板，讀得出是白狗；色票照 `home-hero-turnaround-loop` 的決定「人物改成圓頭、點點眼睛與膚色」記的「色票照舊鎖在路線頁那套」，不加顏色。不會動，跟 `home-hero-turnaround-loop` 的非目標「調度站裡站長的動作」同一個原則。

這條決定的代價：`home-hero-turnaround-loop` 的非目標「放大成停車場、同時有好幾台車進出」記下的風險是圖讀起來像玩具（讀者是公運處、審議會、記者），狗是往可愛那邊推。牠只有約 32×23 CSS px、在室內，使用者看過實際大小之後決定放。用這種畫法，牠讀起來是「白色、尖耳、捲尾巴的狐狸犬」，分不出是不是薩摩耶，品種由 alt 文字寫明。

替代方案：

- 趴著（使用者看過之後選了坐著）。
- 純白 `#ffffff` 的毛（不需要：slate-100 襯著地板已經讀得出白，色票也不用多一個顏色）。
- 放大 1.2 到 1.3 倍讓它好認（暫不採用：使用者看過實際大小沒有要求）。
- 墊子或狗窩（不需要：牠襯著地板已經看得出來）。

### 車頭路線牌在司機下車到前門關好之間跑「暫停服務」

`bus()` 在那塊空白路線牌的外側多一片 1.9×0.28 的平面，中心在公車座標 (`front` + 0.025, 2.88, 0)，轉 π/2 面向 +x，用不受光的 `MeshBasicMaterial`，貼圖是 canvas 畫的一條字帶。平面平常不顯示，看到的就是原本的空白路線牌；亮的時候平面蓋在它前面，所以 LED 字不受太陽光的影響，一直是同一個亮度。平面是公車的一部分，`buildScene()` 對整台公車呼叫的 `clipToBlock()` 一樣會給它切面的材質（複製材質、共用同一張貼圖）。

字帶（`CanvasTexture`，`colorSpace` 設成 sRGB）：高 64 px，寬是字寬加上牌子的寬（434 px）。先在 slate-800 的底上，把 amber-400 的「暫停服務」畫在最左邊，後面留一段跟牌子一樣寬的空白，字跑完一輪會整個離開牌子，再從右邊進來。貼圖的 `wrapS` 設成重複，`repeat.x` 是牌子寬除以字帶寬，牌子一次只看到字帶的一段。視窗超過字帶尾端時，貼圖重複，接上的是字帶的開頭，所以字一律從牌子右邊進來、往左離開，不會從左邊冒出來；原型逐 0.2 秒看過第 3.8 到 11.0 秒的車頭，第 7.6 秒前後是兩輪之間的空白。字用瀏覽器有的字型，字型清單同海報；靜態圖在開發機上匯出，用的是 PingFang TC。

`bus()` 回傳的物件多一個 `sign`（平面與它的貼圖），`buildScene()` 放進 `parts.sign`。`pose(parts, seconds)` 用一圈裡的秒數設兩件事：

1. 平面在 [`TIMELINE.stepOut` 的開始, `TIMELINE.doorClose` 的結束)，也就是 [3.8, 11.0) 秒之間顯示，其他時間隱藏。用時間軸的常數，不另外寫數字，時間軸調了它跟著動。
2. 貼圖的 `offset.x` 是 `((字寬 − 牌子寬) / 2 + (秒數 − STILL) × 150) / 字帶寬`，在 `STILL` 時字剛好置中，之後每秒往左移 150 px。

匯出頁一律用 `pose(parts, STILL)`，所以兩張靜態圖上的路線牌是整句置中的那一格；`runtime.js` 每一格都呼叫 `pose()`，跑馬燈不用另外接，它只多一步開始前的準備（見「首頁在畫第一格之前，先編譯好所有材質、上傳貼圖」）。`scene.js` 開頭色票那段註解，`AMBER_400` 的用途補上路線牌的字；`bus()` 上方的註解把「a blank destination sign」改成平常空白、司機在外面時跑「暫停服務」。

理由：

- 只亮車頭：使用者看過「只亮車頭、加一塊寫實大小的側面牌、側面牌放大」三種做法的實際大小後選的（2026-10-24），接受桌機的全景上讀不出字、只看得到一小塊琥珀色在跑。手機上路線牌比較大，估計勉強讀得出字（看原型圖判斷的，5.1 在手機上確認）。
- 第 3.8 秒亮：使用者說「司機下車的時候」，也就是 `stepOut` 的開始，前門已經開好。
- 第 11.0 秒熄：使用者說「啟動準備載客的時候」。前門關好（`doorClose` 的結束）跟公車開始往站牌開（`pullUp` 的開始）在時間軸上是同一秒，「門合上、字熄掉、車開走」看得出前後關係。這是建議值，使用者沒有提出異議。
- 熄了回到空白：公車是通用車，`home-hero-turnaround-loop` 的決定「人物改成圓頭、點點眼睛與膚色」列為照舊的「沒有業者塗裝、路線號碼、機關標誌」不變，「暫停服務」不屬於這三樣。公車開進來時路線牌是空白的，跟現在一樣，所以同一個決定之下的「一台公車與三個民眾重複使用，地塊左右兩緣都切」寫的「同一台再開進來讀起來就是下一台」照樣成立。
- 琥珀色：路線牌的字是 amber-400 的第三個用途（前兩個是站牌與排班板的格子），不加顏色；真的公車路線牌也常是琥珀色的 LED。
- 不受光的材質：LED 是自己發光的，用 Lambert 的話，車頭面背光時字會跟著暗下去。

替代方案（使用者看過之後沒有選，或比較過後不用）：

- 車身側面前門後面那扇窗上方加一塊寫實大小的牌子（1.0×0.25），Retina 桌機上勉強讀得出字。
- 側面牌放大成 2.3×0.42，跨過兩扇窗，蓋過中間的窗柱，讀得清楚，但比真的公車大一倍以上，像貼了一條橫幅。
- LED 點陣字：這個大小下，點陣只會糊成一條線。
- 司機一進車（`stepIn` 的結束，第 10.2 秒）就熄：比門關好早 0.8 秒，熄燈的那一刻沒有對應的動作。
- 前門一開（第 3.0 秒）就亮：比使用者說的「司機下車的時候」早。

### 規格把「不顯示任何 figure」寫成「任何數字」

`home-page` 的「Hero picture」原本寫「The animation SHALL NOT show a clock, a countdown or any other figure」。figure 在英文可以是數字，也可以是圖形或人形，加了「暫停服務」之後，讀規格的人可能把這四個字當成違反。這條要求來自 `home-hero-turnaround-loop` 的非目標「動畫裡的時鐘、倒數或任何數字」，理由是車停多久只是示意、首頁不放指標，管的是數字。所以把 figure 改成 number，意思不變，並在同一段寫上路線牌何時亮、何時空白，加一個情境「Destination sign while the driver is out」。

替代方案：保留 figure，另外加一句「路線牌的字不算 figure」（不用：改成 number 一次說清楚，不留兩種讀法）。

### 兩張靜態圖重新匯出，alt 文字補上薩摩耶與「暫停服務」

狗與路線牌都在定格畫面裡，兩張 WebP 要從新的場景重新匯出，做法同 `home-hero-turnaround-loop` 的 7.3：用匯出頁的兩個匯出按鈕，存成 `app/assets/images/home-hero-wide.webp` 與 `app/assets/images/home-hero-narrow.webp`，再匯出一次跟剛存的檔比對，0 個像素不同才算數（規格的「Still matches the static image」，以新檔為準）。窄螢幕那張只多了亮著的路線牌，狗在框外。

檔案大小：原型的全景圖（白底、品質 92 的 WebP）加了狗與路線牌之後，比沒加的大約多 1%（59,240 對 58,672 bytes，2026-10-24 量的），估計匯出後仍遠在 200 KB 與 120 KB 的預算內，由 `spec/assets/home_hero_images_spec.rb` 確認。

`app/components/home_hero_component.yml` 的 `alt`（`zh-TW` 跟著 `tw`）：

- `tw`：公車停在末站，車頭的跑馬燈亮著「暫停服務」，司機站在車旁休息。一邊是調度站，站長在看排班板，牆上貼著一張『洋流』海報，地上坐著一隻薩摩耶；另一邊是在站牌前等車的民眾，路邊種著樹。
- `en`：A bus waits at the terminal, its sign reading 暫停服務 (out of service), with its driver resting beside it; on one side the station master at the duty board in the dispatch office, with a 洋流 poster on the wall and a Samoyed sitting on the floor, on the other riders waiting at the stop beside the street trees.

桌機上讀不出路線牌的字，alt 是唯一把「暫停服務」寫出來的地方，用螢幕閱讀器的人與搜尋引擎讀得到。

### 效能預算照舊，加了薩摩耶與跑馬燈之後重新量

預算與量法照 `home-hero-turnaround-loop` 的決定「只在看得到、沒暫停的時候重繪」：開發機的 headless Chrome，用 CDP 開 4 倍 CPU 節流，在頁面腳本執行前包住 `requestAnimationFrame`，量每次回呼的執行時間，不計前三次；全景（寬 1400 px、DPR 1）與窄螢幕（寬 390 px、DPR 3，壓到 2）各量至少一整圈，記下格數、中位數、p95 與最大值；首頁動畫的 chunk 用 brotli（q11）與 gzip（-9）量大小。每格不超過 16 ms，chunk brotli 後不超過 200 KB；超出就停下回報，不自己放寬。量到的數字寫在這一節後面。

估計：全場多 14 個 mesh（狗 13 個、路線牌 1 個）與一張 634×64 的貼圖；上一個 change 多 21 個 mesh 時中位數多約 0.5 ms（`home-hero-turnaround-loop` 8.5 量的），這次應該差不多，離 16 ms 很遠。路線牌每格只改貼圖的 `offset`，不重畫 canvas、不重新上傳貼圖。這個估計由 4.1 在同一輪量改之前的版本對照，確認或推翻。

第一次量（apply 4.1，2026-10-24，開發機 Apple M1 Max，量法同上；還沒有先編譯材質）：

- 首頁動畫的 chunk：未壓縮 548,439 bytes，brotli（q11）113,154 bytes，gzip（-9）136,949 bytes，在 200 KB 的預算內。`home-hero-turnaround-loop` 最後記的是 546,412、112,580、136,254。入口 chunk 的 brotli 41,221 bytes 比那時多 517 bytes，是之後的 commit `ca14701`（路線頁的折返設施卡片）造成的：場景的程式只在動畫的 chunk 裡，入口 chunk 裡找不到。
- 每格耗時：全景（canvas 1088×518）量兩次，中位數 3.4 與 3.8 ms、p95 4.3 與 4.9 ms，最慢 13.3 與 14.7 ms；窄螢幕（canvas 716×477）量三次，中位數 2.4、3.3、2.7 ms，p95 3.5、4.5、3.8 ms，最慢 268.3、18.3、15.5 ms。最慢的一格超過 16 ms，照預算停下回報；原因與修正見下一節。
- 中位數比 `home-hero-turnaround-loop` 記的 2.2 與 1.8 ms 高，但同一份程式重量就差到 0.9 ms，量的時候匯出頁的 Vite 與 test 環境的 Rails 也開著，不能算在這次的改動上；由修正後的量測與改之前的版本對照。

修正後再量的數字接在這一段後面。

先編譯材質之後再量（apply 4.1，2026-10-24，同一台開發機、同樣的量法，每次 26 秒；同一輪把 `ca14701`，也就是這個 change 開始時的程式，另外 build 出動畫 chunk，暫時換進 `public/vite` 量，量完重新 build 換回來）：

- 首頁動畫的 chunk：現在未壓縮 548,521 bytes，brotli（q11）113,109 bytes，gzip（-9）136,977 bytes；改之前 546,412、112,580、136,254 bytes，跟 `home-hero-turnaround-loop` 記的一樣。在 200 KB 的預算內。
- 全景（canvas 1088×518），現在量兩次：中位數 2.9 與 3.6 ms，p95 3.8 與 4.6 ms，最慢 7.1 與 6.9 ms；第 225 格 6.7 與 6.7 ms，兩次都是第二慢。改之前量兩次：中位數 4.3 與 3.6 ms，p95 5.6 與 4.7 ms，最慢 9.7 與 9.2 ms；第 225 格 5.7 與 5.8 ms。
- 窄螢幕（canvas 716×477），現在量五次：中位數 2.2、3.0、3.2、2.9、3.4 ms，p95 2.8、3.9、4.4、3.8、4.4 ms，最慢 7.8、12.3、9.2、10.8、10.2 ms，五次最慢的都是第 224 或 225 格。改之前量五次：中位數 2.9、2.9、2.9、2.9、2.8 ms，p95 4.0、4.0、3.8、4.1、3.7 ms，最慢 9.5、7.7、8.8、7.1、8.0 ms；第 224 或 225 格 6.7、6.6、4.8、6.7、5.6 ms。
- 每格都不超過 16 ms。
- 第一圈第 224、225 格在改之前就比一般的格子慢（4.8 到 6.7 ms）。那一刻司機第一次出現，推測是他身上的形狀第一次畫時要上傳到 GPU，這部分 `renderer.compile()` 管不到；沒有驗證。路線牌在同一刻第一次亮，那一格比改之前多出來的：沒有先編譯時窄螢幕平均約 10.8 ms（16.9 對 6.1 ms）、全景約 9 ms；先編譯之後窄螢幕平均約 4.0 ms（10.1 對 6.1 ms）、全景約 1 ms。
- 中位數看不出差異：窄螢幕五次的平均，改之前 2.88 ms、現在 2.94 ms；全景兩次反而是現在比較低，差異在量測的起伏之內。估計的「多約 0.5 ms」沒有量到。

### 首頁在畫第一格之前，先編譯好所有材質、上傳貼圖

`runtime.js` 的 `start()` 建好場景、renderer 與鏡頭之後，在畫第一格之前多做兩件事：用當下的鏡頭呼叫 `renderer.compile(scene, camera)`，編譯場景裡每個 mesh 的材質；再走過場景，對每個有貼圖（`map`）的材質呼叫 `renderer.initTexture()`，先把貼圖上傳。兩件事都只在 `start()` 做一次，跟第一格一樣不在 `requestAnimationFrame` 的回呼裡。`scene.js` 與匯出頁不改：匯出頁只在定格畫面畫一次，那時路線牌亮著，畫的時候就會編譯，也沒有每格的預算。

為什麼要這一步（apply 4.1 第一次量，2026-10-24，量法同上一節）：

- 有記每格時間的幾次，最慢的都是第一圈的第 224 或 225 格，約第 3.75 秒，正是路線牌第一次亮的時候：全景 14.7 ms，窄螢幕 18.3 與 15.5 ms。下一圈同一時間沒有再慢（量了 26 秒，涵蓋到下一圈的第 3.8 秒）。
- 更早的一次窄螢幕量到最慢 268.3 ms。那次沒有記每格的時間，不能確定是哪一格；推測是 GPU 還沒有這個 shader 的快取，沒有驗證。
- 對照實驗：暫時讓路線牌從第一格就顯示，第 3.8 秒的尖峰消失（那一格 5.5 ms）；窄螢幕最慢的一格移到約第 0.6 秒（11.8 與 13.0 ms），也就是公車開進窄螢幕鏡頭、路線牌第一次被畫出來的那一格。實驗做完就改回來了。
- 所以慢的是「路線牌的材質第一次被畫」：它是不受光、有貼圖、加了地塊切面的 `MeshBasicMaterial`，場景裡沒有別的材質用同一組設定，第一次畫時要編譯一個新的 shader，再上傳它的貼圖。其他材質都在 `start()` 畫的第一格就編譯好了，那一格不在量的範圍內。狗用的是場景共用的 Lambert 材質，不會多編譯。

做法的依據：three.js r186 的 `renderer.compile()` 準備材質時用 `scene.traverse()` 走過每個 mesh，看不見的也算（只有收集燈光時看 `visible`），但它不上傳貼圖，所以另外呼叫 `renderer.initTexture()`。對整個場景做、不只針對路線牌：一開始畫不到的東西以後再加也照樣有保障，`runtime.js` 也不用知道場景裡有路線牌。第一格本來就要編譯場景裡畫得到的所有材質，多的只有路線牌那一個 shader 與一張貼圖（開發機上 634×64）。

跟 `home-hero-turnaround-loop` 的決定「只在看得到、沒暫停的時候重繪」一致：canvas 插進去時照樣先畫第一格；預算與量法照舊，超出就停下回報、不自己放寬。

替代方案：

- 只在 `scene.js` 處理：路線牌熄著的時候也一直畫，只是不寫入顏色與深度，讓它在第一格就編譯。對照實驗顯示，窄螢幕的鏡頭一開始框不到公車，成本只是移到第 0.6 秒（11.8 到 13.0 ms）；讀程式的人也看不出為什麼熄掉時還要畫。不用。
- 只針對路線牌：`renderer.compile()` 加上 `renderer.initTexture(parts.sign.texture)`。程式一樣短，但 `runtime.js` 要知道場景的細節，以後再有一開始畫不到的東西又要改。不用。
- `renderer.compileAsync()`：不會卡住主執行緒，但要等它完成才開始畫，`start()` 得改成非同步；`app/frontend/entrypoints/application.js` 的 `homeHero` 元件同步拿 `start()` 回傳的 `toggle()` 與 `dispose()`，也要跟著改。這個成本本來就落在不算預算的第一格，同步編譯就夠了。不用。
- 放寬預算，或把第一次畫某種材質的那一格排除在預算外：使用者沒有選（2026-10-24）。
- 在第一格之前，先用全景鏡頭把定格畫面畫一次：所有東西在開場前都畫過，路線牌剩下的成本（見上一節，窄螢幕約 4 ms、全景約 1 ms）與司機第一次出現的那一下都會消失；代價是開場多畫一格，也依賴定格畫面看得到所有東西（後門的一片門板例外）。先編譯之後每格已經在預算內，使用者看過 4.1 的量測後選擇接受剩下的成本（2026-10-24），不用。

## Implementation Contract

行為（看的人看到什麼）：

- 有 JS、允許動態、有 WebGL 的桌機：調度室窗後的地上坐著一隻白色的薩摩耶，一直不動。公車停好、前門打開、司機開始下車時，車頭擋風玻璃上方的路線牌亮起來，琥珀色的「暫停服務」由右往左跑；司機回到車上、前門關好時熄掉，回到空白，公車開去站牌。一圈裡其他時候路線牌都是空白的。桌機上讀不出字，只看得到一小塊琥珀色在跑。路線牌第一次亮起來的那一格也在每格 16 ms 的預算內。
- 手機（窄於 640 px）：跟桌機一樣的路線牌，畫面裡比較大；看不到調度室與狗。
- 減少動態效果、沒有 WebGL、動畫 chunk 載不到、頁面腳本沒有接手：看到重新匯出的靜態圖，全景有狗，兩張的路線牌都亮著、整句置中；alt 文字寫到薩摩耶與「暫停服務」。

介面與資料形狀：

- `app/frontend/hero/scene.js` 新增 `samoyed()`（回傳一個 `THREE.Group`），由 `dispatchOffice()` 放進調度室；不在 `parts` 裡。
- `bus()` 的回傳值多一個 `sign`，裡面有路線牌的平面與它的 `CanvasTexture`；`buildScene()` 回傳的 `parts` 多一個 `sign`；`pose(parts, seconds)` 依一圈裡的秒數設平面的 `visible` 與貼圖的 `offset.x`。`CYCLE`、`STILL`、`TIMELINE` 與其他匯出的函式不變。
- `app/frontend/hero/runtime.js` 的 `start()` 在第一次 `render()` 之前，用當下的鏡頭呼叫 `renderer.compile(scene, camera)`，再對場景裡每個有 `map` 的材質呼叫 `renderer.initTexture()`；`start()` 照舊同步回傳 `toggle()` 與 `dispose()`，其他流程不變。
- `tools/hero/index.html`、`tools/hero/export.js` 不改。

失敗的情況：

- 裝置上沒有清單裡的中文字型：字會變成方框，跟海報一樣接受；靜態圖照樣用開發機的 PingFang TC 匯出。
- 其他跟現在一樣：動畫的 chunk 載不到就退回靜態圖；render 丟出錯誤不攔。

驗收：

- 規格的「Destination sign while the driver is out」：路線牌亮不亮由秒數決定、捲到哪裡是算出來的，照 TDD 的測試範圍是要測的條件分支，但專案的測試環境觀察不到（沒有 JS 的測試工具，`scene.js` 建場景要用瀏覽器的 canvas；首頁的 canvas 不保留畫面、讀不出像素；`parts` 與 `pose()` 從頁面拿不到；`tools/hero` 只在 Vite 底下跑），所以不寫自動測試、這一項記為未驗證，改用匯出頁的 `?s=` 在情境 Example 的每個秒數（1.5、3.4、4.2、5.5、10.6、11.2、14.4）各截一張全景與一張窄螢幕的圖，裁出車頭放大看，路線牌的狀態跟表一致。
- 狗：匯出頁 `?s=5.5` 的全景圖裁出調度室放大看，狗整隻在窗洞裡，不擋站長、桌子、排班板與海報，跟原型的調度室特寫一致。
- 匯出頁在 `STILL` 匯出的兩張圖，跟 `app/assets/images/` 的 WebP 用 `magick compare -metric AE` 比對是 0（重新匯出後以新檔為準，再匯出一次比對）。
- `spec/assets/home_hero_images_spec.rb`、`spec/components/home_hero_component_spec.rb`、`spec/system/home_hero_spec.rb` 不用改、照樣通過；`bin/ci` 通過。
- alt 文字做內容審閱：`tw` 與 `en` 都寫到薩摩耶與「暫停服務」。
- 每格耗時與 chunk 大小在預算內，數字寫回「效能預算照舊，加了薩摩耶與跑馬燈之後重新量」。

- 使用者用 `bin/dev` 在 1280 px 與 390 px 寬看過。

## Risks / Trade-offs

- [桌機上讀不出路線牌的字] → 使用者看過實際大小後接受（2026-10-24）；alt 文字寫出「暫停服務」。
- [狗把插圖往可愛那邊推，讀者是公運處、審議會、記者] → 牠只有約 32×23 CSS px、在室內、不會動；使用者決定放，最後由 `bin/dev` 的人工確認看實際大小。
- [跑馬燈是一直在動的東西，WCAG 2.2.2 要求超過 5 秒的動態內容能停] → 它是動畫的一部分，插圖現有的暫停鈕、減少動態效果與捲出畫面就停照樣管得到。
- [路線牌的平面與原本的方塊重疊閃爍] → 平面在方塊外側 0.005；用匯出頁在亮的時段截幾格放大看，閃爍就把距離加大。
- [車頭這一面是斜著看的，被壓到約四成寬，取樣會落到較小的 mipmap，字糊成一團] → 由 2.1 的車頭截圖判斷；糊掉就試把貼圖的 `minFilter` 改成 `LinearFilter`（不用 mipmap）或調高 `anisotropy`，挑截圖最清楚的那個。實際大小下本來就讀不出字，這條只影響手機與放大看的時候。apply 2.1 試過三種（2026-10-24，開發機 GPU 匯出）：預設的 mipmap 字偏糊；`LinearFilter` 停格最銳利，但相隔 1/60 秒的兩格筆畫碎成不同的鋸齒，動起來會閃；`anisotropy` 設 16（three.js 會壓到 GPU 支援的上限）比預設清楚、連續幾格穩定，採用這個。
- [字型在不同裝置上不同，字寬不是 200 px] → 字寬在建貼圖時用 `measureText` 量，置中照量到的寬算，不寫死。
- [靜態圖跟定格畫面對不上] → 匯出兩次比對到 0 才算數；不是 0 就找出差異來源，不自己改規格。
- [多了 14 個 mesh 與一張貼圖] → 重新量每格耗時與 chunk 大小，超出預算就停下回報。
- [`renderer.compile()` 準備的設定跟實際畫的時候對不上，路線牌第一次畫時還是重新編譯] → 由 4.1 跟改之前的版本比第一圈第 225 格附近；超出預算就停下回報。4.1 量到（2026-10-24）：先編譯之後那一格比改之前多約 4 ms（窄螢幕）與 1 ms（全景），沒有先編譯時多約 10.8 ms 與 9 ms，每格都在 16 ms 內；剩下的推測是 `renderer.compile()` 管不到的第一次畫的工作，沒有驗證。使用者選擇接受（2026-10-24）。
- [先編譯讓第一格變慢] → 多的只有路線牌一個 shader 與一張貼圖；第一格不在 `requestAnimationFrame` 的回呼裡，不算進每格的預算。
