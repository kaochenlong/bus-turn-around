## 1. 推法：瀏覽器端的純函式

- [x] 1.1 趟次帶上原本的發車時刻與是不是打的，照 design「推法是一個純函式，每次修改後重算整張單」：`layOut` 排出來的每一趟都多 `typed: false` 與等於發車的 `original`，`plan()` 的回傳形狀不變；`app/frontend/timetable/support.js` 的 `trip()` 預設 `typed: false`、`original` 等於發車，可以用選項覆寫。先在 `app/frontend/timetable/layout.test.js` 加「鋪排出來的趟次 typed 是 false、original 等於發車」看它失敗，再改 `layOut`。驗證：`yarn test:js` 全綠，原本拿 `plan()` 整個比對的那一條不用改。
- [x] 1.2 Manual edits recomputed in the browser 的推法本身，照 design「鋪排與微調都在瀏覽器算，改時刻後沒打過的趟次往後推到停滿」與「推法是一個純函式，每次修改後重算整張單」：`app/frontend/timetable/edits.js` 新增 `settle(trips, plan, holds)`，從第一趟往後逐趟算——打的趟次照打的時刻發；第一趟不是打的就從 `original` 發；其他不是打的趟次從 `original` 與「前一趟到達＋`holds[前一趟的 goBack]`」較晚的那個發；到達用 `plan()` 重算，帶回原來的 `edited`、`typed`、`original`，回傳新陣列、不改傳入的。另外新增 `pushedMinutes(trip)`（不是打的才算，發車減 `original`，沒被推是 0）與 `countPushed(vehicles)`。先在 `app/frontend/timetable/edits.test.js` 寫測試看它失敗：兩列的單（06:00–06:50、07:30–08:15、09:30–10:20、10:35–11:20，去程每小時 50 分、返程 45 分，停留都是 15）第一趟改成打的 08:00 時，發車是 08:00、09:05、10:05、11:10；第一趟打的 07:00 時只有第二趟推到 08:05、後面不動；不是打的趟次不早於 `original`；打的趟次不動、它前面的停留照實是負數；不改傳入的陣列；`pushedMinutes` 與 `countPushed` 的值。驗證：`yarn test:js` 全綠。[after: 1.1]
- [x] 1.3 Manual edits recomputed in the browser 的四種修改都照推法重算，照 design「只有打過的時刻固定，加列與加一台車算出來的返程也照推」：`changeDeparture(vehicles, { vehicle, index, departure }, plan, holds)` 把打的那一趟設成 `typed: true`、`original` 等於打的時刻、`edited: true`，再 `settle` 那張單；`deleteRow(vehicles, { vehicle, row }, plan, holds)` 刪完之後 `settle`；`addRow` 與 `addVehicle` 的第一趟 `typed: true`、返程 `typed: false`、`original` 等於加的當下算出的「到達＋停留」，兩趟照舊 `edited: true`，再 `settle`。先在 `app/frontend/timetable/edits.test.js` 寫測試看它失敗：規格例子「First departure typed」的四列（06:10、05:30、07:00、08:00，含被推過的格子與分鐘數）、「Typed departures are not pushed」（−50、只有 09:05 被推）、「Deleting a row lets later trips go back」、改成 06:45 推到 07:50 之後再改回 06:00 回到 07:30、「The return of an added row follows its first departure」（12:33、兩格 `edited`、推了 30 分）；原有的 `changeDeparture` 與 `deleteRow` 測試改成傳 `planner` 與 `holds`，結果不變，`changeDeparture` 那一組的標題改成「改一趟的發車，後面沒打過的接不上就往後推」。驗證：`yarn test:js` 全綠，原有的「改成 06:45 也照改」「刪第一列」「規格的加列」「規格的加車」照舊綠。[after: 1.2]

- [x] 2.1 Header, controls and limitations of the timetable 的頁首多一個被推過的格數，照 design「被推過的格子用自己的標記，頁首另外數」：`TimetableHeaderComponent#figures` 在 `edited` 後面多一個 `pushed`，伺服器先放「—」由瀏覽器填；`app/components/timetable_header_component.yml` 的 tw 加「跟著往後推」、en 加對應的標籤，單位沿用 `edited_unit` 的「處」。先把 `spec/requests/timetables_spec.rb` 與 `spec/components/timetable_header_component_spec.rb` 列頁首數字的那一條都加上 `pushed`、期待「—」，看它失敗。驗證：`bundle exec rspec spec/requests/timetables_spec.rb spec/components/timetable_header_component_spec.rb` 全綠；標籤文字做內容檢查。
- [x] 2.2 Manual edits recomputed in the browser 在頁面上：元件把推法接上、被推過的格子有標記，照 design「被推過的格子用自己的標記，頁首另外數」：送出發車、刪列、加列、加一台車都把 `this.planner()` 與 `this.holds()` 交給 `edits.js`；`departureCell` 在被推過的格子帶 `data-pushed`、淡琥珀色的底與框（只在被推過時生效、蓋得過 `bg-white` 與 `border-slate-300`），`title` 用單子 template 新增的 `data-pushed-title`（「跟著往後推 %{minutes} 分，原本 %{time}」，tw 與 en 寫在 `app/components/timetable_sheet_component.yml`），同時手動改過時兩句用「；」接；`writeFigures` 填 `pushed`。先在 `spec/system/timetable_edit_spec.rb` 的「手動微調」寫測試看它失敗：「1 號車去程打 06:45：那一列 06:45、甲站、07:35、15、07:50、08:35，07:50 帶 data-pushed、說明含 20 與 07:30，頁首改過 1、跟著往後推 1，2 號車不動」、「再打回 06:00：那一列回到 06:00、甲站、06:50、40、07:30、08:15，跟著往後推 0」、「被推過的 07:50 照原樣打 0750：仍帶 data-pushed、沒有 data-edited，頁首照舊 1 與 1」、「加一列 11:00 再把去程改成 11:30：那一列 11:30、甲站、12:18、15、12:33、13:19，12:33 同時帶 data-edited 與 data-pushed」。這幾個例子只用 fixture 已經補了五趟的小時（去程 06、11 時，返程 07、12 時），用到別的小時要先補趟次，不然到達會帶 ＊。驗證：`bundle exec rspec spec/system/timetable_edit_spec.rb` 全綠，原有的「改成 06:45 接不上：停留印 −5」、焦點、退回的例子照舊綠；每個例子不超過 5 行；底色與框色在 3.2 截圖給使用者看。[after: 1.3, 2.1]
- [x] 2.3 Header, controls and limitations of the timetable 的資料限制改寫負停留那一行：`app/components/timetable_limitations_component.yml` 的 tw 改成「停留印成負數，表示手動打的時刻比前一趟到達還早；沒打過的趟次接不上時，會往後推到停滿那一端的停留，打過的不會動」這個意思，en 同步改寫。先在 `spec/requests/timetables_spec.rb` 加「資料限制寫著負停留是手動打的時刻比前一趟到達還早，沒打過的會往後推」看它失敗（照規格「Limitation of negative stops」）。驗證：`bundle exec rspec spec/requests/timetables_spec.rb` 全綠；en 那一行做內容檢查。[after: 2.1]
