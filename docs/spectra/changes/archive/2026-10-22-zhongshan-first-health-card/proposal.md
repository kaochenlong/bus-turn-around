## Why

這個 change 服務三樣交付物的第一樣：路線健檢卡。它做的是中山幹線的第一張卡，而且只用 2026-10-19 這一個台北日的資料，目的不是給人引用的數字，是驗定義：趟次怎麼切、折返停留怎麼算、車上人數可不可信、漏了多少站。`docs/background.md` 的「順序」一節把這一步定為止損點：資料收滿一整天之後，先做中山幹線、只做折返停留和載客剖面、用 DuckDB 直接查、輸出 Markdown。2026-10-19 是採集開始後第一個完整的台北平日，條件在今晚午夜成立。

每晚批次、衍生表、路線頁都要建立在同一套趟次與折返停留的定義上。定義沒有在真資料上驗過就進 Rails，等於把猜測固化成 schema。這張卡先把定義逼出來，之後的 change 再把驗過的 SQL 搬進批次。

需要的資料全部已經在手上，都是 n-gear 收的原始檔，不需要任何外部資料集：

- 動態 feed `bus_event`（到離站）：重建趟次、算折返停留、算漏站。
- 動態 feed `bus_seat_event`（車上人數 `RemainingNum`、擁擠等級 `Level`）：載客剖面、淨上下車、歸零檢查。
- 靜態 feed 同一天的快照 `GetRoute.gz`（路線 `Id` 對附屬路線 `pathAttributeId`、起迄、班距）與 `GetStop.gz`（每方向的站牌 `Id` 與 `seqNo`）：站序與方向。
- 辦公日曆不需要：2026-10-19 是週一平日，一天版不分日型別。

## What Changes

- 新增一組 DuckDB SQL 與一支不載入 Rails 的 Ruby 執行檔，輸入是原始檔的資料根目錄、路線 `Id`、台北日，輸出是一份 Markdown 健檢卡與一份只供本機檢查的逐趟 CSV。
- 趟次重建：以 `(BusID, DataTime)` 去重後，把中山幹線三條附屬路線（15373、162347 去程半、162348 反程半）的到離站事件依車牌、路線、方向切成趟次，標記每趟是否完整（起站、末站都有事件）。讀檔視窗是前一天最後兩小時、當天全部、隔天前兩小時：跨午夜的趟次歸發車那一天，前一晚發車、跨過午夜的趟次也不會被算成當天的趟次。
- 折返停留：同一車牌相鄰兩個完整趟次之間的間隔。給 p10、p50、p90、不到 15 分鐘的比例，以及依汽車運輸業管理規則第 19 條之 2 的門檻（任何連續 4 小時內、每段至少 15 分鐘的停留累計不到 30 分鐘）標出的班次串數。
- 載客剖面：每趟逐站的車上人數，按方向與時段彙總；相鄰兩站相減得淨上下車；每個完整趟次在起站上客前（起站的到站記錄）與末站下客後（末站的離站記錄）的車上人數，按方向分列並標出站名，回答「RemainingNum 每趟是否歸零」。
- 資料品質一節：事件筆數、去掉的重複筆數、完整與不完整趟次數、漏站率、`DutyStatus` 的分佈與它跟趟次邊界的對應；三條附屬路線各有幾趟是那台車當天在這條路線的第一趟或最後一趟，回答業者什麼情況下掛去程半與反程半；每個方向的完整趟次中，末站在終點後有離站事件的趟數。這一節就是這張卡存在的理由。
- 卡上一律是路線層級的彙總，不出現任何車牌；逐趟 CSV 寫到 `tmp/` 下、不進版本控制。
- 卡帶「資料限制」一節與 OGDL-Taiwan-1.0 顯名聲明，文字照 `docs/data-sources.md`。
- 用合成的 JSONL fixture 寫 RSpec 鎖住每一條切趟與算法規則；測試需要 DuckDB CLI，機器上沒有時整組明確標示略過。
- 跑出來的 2026-10-19 一天版卡放進 `docs/cards/`。

## Non-Goals

非目標，這個 change 不做：

- Rails 頁面、路線頁、ViewComponent、任何 PostgreSQL 衍生表。第一張卡的 SQL 驗過之後，搬進每晚批次是下一個 change。
- 排程、每晚自動重跑、月卡。這一張是手動跑一次的一天版，數字不能拿去引用。
- 班表對照（脫班、班距達成）、捷運重疊與競爭力、折返點設施、門檻對照裡的 70% 與 5 人、建議動作。卡上這些欄位先不出現，不留空殼。
- 其他路線。路線 `Id` 是參數，但只在中山幹線上驗過；307、251 區間、捷運接駁、預約公車等五條線的第二張起另開 change。
- 接近零與滿載的門檻判定。一天版只給剖面表，不下判斷。
- 平假日分開算。一天沒有這個問題。
- 外部資料集（辦公日曆、捷運出入口、公廁）、TDX、票證 OD。
- 改 n-gear。採集端不動；營運通阻要不要抓得更密另案。
- 用 Ruby 的 `duckdb` gem。`docs/decisions.md` 第 3 條定的是起一個 process 跑 SQL 然後結束，gem 要先裝 libduckdb，這裡用 CLI 子行程。
- 把這一天的任何數字寫進 `docs/background.md` 或 README 當結論。

## Capabilities

### New Capabilities

- `trip-reconstruction`：從一條路線一個台北日的到離站事件重建趟次：去重、台北日視窗、附屬路線對路線與方向、切趟、完整性標記、跨午夜歸屬。
- `layover-metrics`：同一車牌相鄰完整趟次之間的折返停留，分佈統計、不到 15 分鐘的比例、依第 19 條之 2 門檻標出的班次串。
- `load-profile`：每趟逐站車上人數、淨上下車、按方向與時段的剖面彙總、起站上客前與末站下客後的歸零檢查。
- `health-card`：執行檔與 Markdown 卡：輸入與參數、各節內容、資料品質數字、資料限制與顯名、不出現車牌、逐趟 CSV 另存。

### Modified Capabilities

無。這個 repo 目前沒有任何既有的 spec。

## Impact

- 新增 `analysis/` 目錄放 SQL 檔與一份說明；新增執行檔 `bin/health-card`（純 Ruby stdlib，用 `Open3` 呼叫 `duckdb`，不載入 Rails）。
- 新增 `spec/analysis/` 的 RSpec 與 `spec/fixtures/analysis/` 的合成 fixture（假車牌、假站序，涵蓋完整趟、漏起站、跨午夜、換附屬路線、跨小時檔重複、歸零異常、起站上客前與末站下客後的記錄）。
- 修改 `.rubocop.yml`：對 `spec/analysis/` 關掉 `RSpec/DescribeClass`，因為那些 spec 測的是 SQL、fixture 與執行檔，沒有 Ruby 類別可以 describe；rubocop-rspec 原本對 requests、system 等目錄的排除保留。
- 新增 `docs/cards/` 放跑出來的 Markdown 卡。
- 開發機與 CI 多一個外部二進位依賴：DuckDB CLI。不改 `Gemfile`，不改 Rails 設定，不碰資料庫 schema。
- 資料根目錄只透過參數或環境變數傳入，repo 裡不出現主機或備份路徑（`docs/decisions.md` 第 11 條）。
- 資料限制與假設，卡上與 spec 裡都要寫明：車不等於人，折返停留是駕駛休息的上限，雙班制下對不回單一駕駛；車上人數是票證推出來的值，準確度看下車刷卡率與歸零邏輯；10 秒輪詢一定漏站，完整趟次的判定與漏站率是這張卡要量的東西，不是已知；跨小時檔的重複在壓縮時沒處理，讀檔時一律再去重；一天的樣本太少，離峰時段一個方向只有幾趟，所有百分位數只用來看定義對不對。
