## Context

採集器 n-gear 從 2026-10-18 起每 10 秒收三支動態 feed，每天 04:30 快照 19 支靜態 feed，原始檔以 `<feed>/<台北日>/<HH>.jsonl(.gz)` 與 `static/<台北日>/<原始檔名>.gz` 存放。2026-10-19 是第一個完整的台北平日。website repo 目前只有 Rails 骨架，`docs/spectra/specs/` 沒有任何 spec，沒有任何分析程式。

這個 change 做的是 `docs/background.md`「順序」一節的止損點：用 DuckDB 直接讀原始檔，為中山幹線（路線 `Id` 15373）做一天版的健檢卡，只做折返停留與載客剖面兩項，輸出 Markdown。它的產出是定義，不是結論。

已經核對過的事實（2026-10-19 的快照與事件，以及 2026-10-18 最後一小時的事件）：

- 事件的 `RouteID` 是附屬路線 `pathAttributeId`。中山幹線在 `GetRoute.gz` 有三列，`Id` 都是 15373，`pathAttributeId` 分別是 15373「中山幹線」、162347「中山幹線去程半」、162348「中山幹線反程半」。
- `GetStop.gz` 以路線 `Id` 為 `routeId`，每個方向各一組站牌 `Id`，`seqNo` 兩方向連號：去程 0 到 45、返程 46 到 90。162347 的站序等於整段去程，162348 等於整段返程；事件裡 162347 只出現 `GoBack` 0，162348 只出現 `GoBack` 1。
- `GetPathDetail.gz` 的 `sequenceNo` 每條附屬路線各自從 0 起算：15373 是 0 到 90 共 91 站，等於去程接返程；162348 是 0 到 44。三支靜態檔都是單一 JSON 物件，資料列在外層的 `BusInfo` 陣列裡，旁邊是 `EssentialInfo`。
- `DutyStatus` 只有 1 和 2，2 約佔 0.6%。`DataTime` 是台北時間、無時區；`_fetched_at` 是 UTC；小時檔依 `_fetched_at` 的台北時間分區。
- 2026-10-19 的 00 時檔有三台中山幹線的車從 00:00 起有事件，三台在 2026-10-18 的 23 時檔都有同方向、一路到 23:58 至 23:59 的事件；00 時檔沒有任何一筆的 `DataTime` 落在 2026-10-18。
- 筆電原本沒有 DuckDB CLI，任務 1.1 裝了 1.5.6，確認 `read_json` 接受 `getvariable()` 當路徑，結果記在 `analysis/README.md`。`docs/decisions.md` 第 3 條定了分析引擎用 DuckDB、排程就是起一個 process 跑 SQL；第 5 條定了原始檔「允許重複、不漏」、下游一律再去重；第 11 條定了營運細節不進公開 repo。

詞彙依 `docs/spectra/LANGUAGE.md`：趟次、折返停留、附屬路線、台北日、車上人數、淨上下車、漏站、班次串。

## Goals / Non-Goals

**Goals:**

- 用一份能重跑的程式，從原始檔算出中山幹線 2026-10-19 的趟次、折返停留、載客剖面與資料品質數字，輸出一份 Markdown 卡。
- 把每一條切趟與算法規則寫成可以用合成 fixture 測的行為，讓之後搬進每晚批次時有東西可以對。
- 回答五個定義問題：趟次切法對不對、去程半與反程半怎麼併、`RemainingNum` 是否每趟歸零、漏站率多少、`DutyStatus` 2 是不是趟次結束。`RemainingNum` 的答案出現在卡的載客剖面一節，其餘出現在資料品質一節，都不寫進任何文件當結論。

**Non-Goals:**

- Rails 頁面、ViewComponent、PostgreSQL 衍生表、排程與每晚重跑。
- 月卡、平假日分開算、任何可以引用的數字。

- 接近零與滿載的門檻判定。
- 其他路線的驗證；路線 `Id` 是參數，但只在中山幹線上跑過。
- 改 n-gear、改 `Gemfile`、改 `bin/setup` 或 `bin/ci`。
- 用 Ruby 的 `duckdb` gem。

## Decisions

### 用 DuckDB CLI 子行程跑 SQL 檔，變數用 SET VARIABLE 傳入

執行檔 `bin/health-card` 是純 Ruby stdlib（`optparse`、`open3`、`json`），不載入 Rails，也不用 `csv`：Ruby 3.4 起 `csv` 不再是預設 gem，不改 `Gemfile` 就無法在 bundler 底下載入，而 CSV 本來就由 DuckDB 的 `COPY` 寫出，測試要讀回時也交給 DuckDB 的 `read_csv`。執行檔組一段前置 SQL 設定變數（資料根目錄、路線 `Id`、台北日、靜態快照日、檢查輸出目錄），先接 `analysis/params.sql`，再接 `analysis/` 底下依檔名排序的編號階段檔，整段餵給 `duckdb -no-init -bail -batch -json` 子行程，用 JSON 取回要渲染的結果。順序固定是 `params.sql` 先、編號階段後：單純照檔名排，`params.sql` 會排在 `60_export.sql` 之後，前面的階段讀常數只會拿到 NULL。SQL 檔用 `getvariable('data_root')` 這類呼叫取參數，所以在 `duckdb` 互動 shell 裡先 `SET VARIABLE` 再 `.read` 同一批檔案也能跑，方便探索。

替代方案：Ruby 的 `duckdb` gem（native extension，要先裝 libduckdb，決定第 3 條已排除）；在 Ruby 端做字串模板把參數塞進 SQL（可行，但 SQL 檔就不能單獨在 shell 裡跑）。原本預留的退路是：若 `read_json` 這類 table function 不接受 `getvariable()` 當路徑參數，就退回只替換 `{{data_root}}` 一個佔位符的字串模板。任務 1.1 在 DuckDB 1.5.6 上確認可行，不需要退路。DuckDB 要 1.1 以上（`SET VARIABLE` 從 1.1 開始）。

### 讀檔視窗是前一天最後兩小時、當天全部、隔天前兩小時，趟次歸發車那一天

算台北日 D 時，`bus_event` 與 `bus_seat_event` 都讀 D-1 的 22、23 時、D 的全部小時、D+1 的 00、01 時的小時檔。檔案清單用 `glob()` 實際找到的檔組成，視窗內沒有檔的小時直接略過：採集第一天沒有 D-1，最新一天還沒有 D+1。切完趟次後只保留起站離站時刻落在 D 的趟次：D 凌晨那些屬於前一晚趟次的事件，會跟 D-1 最後兩小時的事件接成起點在 D-1 的趟次而被丟掉；D 晚上發車、D+1 凌晨到站的趟次則完整保留。

往前讀，是因為不讀 D-1 時，前一晚發車、跨過午夜的趟次只剩 D 凌晨那一段，會被算成 D 的 00:00 出發、漏起站的趟次；2026-10-19 的 00 時檔就有三台車是這樣。往前讀的時數至少要是切趟中斷門檻的兩倍：開頭被視窗切掉的趟次，視窗裡的第一筆最晚在視窗起點後一個門檻內出現，它在那一站的離站最晚再晚一個門檻，兩者都落在午夜之前，這一趟的起點才會落在 D-1。小時檔依抓取時刻分區，抓取時刻不早於 `DataTime`，所以 `DataTime` 在視窗起點之後的事件一定在視窗內的檔裡。只讀一小時的反例：一台車 22:59 過倒數第二站（記在 22 時檔）、23:05 到終點、00:02 從終點離站，視窗裡只剩終點站兩筆，起點變成 D 的 00:02。

往後讀兩小時是依中山幹線末班 23:00、單趟不到三小時定的，之後跨夜路線要改成參數再說。往前、往後的時數都寫在參數檔，往前的時數由中斷門檻算出。

替代方案：只讀 D 的檔（23 時發車的趟次被切斷，前一晚的尾巴變成 D 的假趟次）；往前只讀一小時（上面的終點站反例）；讀 D-1、D+1 整天（兩端各多讀十二倍的資料，換不到任何東西）。

### 以 (BusID, DataTime) 去重，兩支 feed 各自做

載入時先以 `RouteID` 過濾成該路線的附屬路線，再去重。同一支 feed 內以 `(BusID, DataTime)` 為鍵，保留 `_fetched_at` 最早的一筆，這是決定第 5 條說的下游再去重。`bus_event` 與 `bus_seat_event` 分開去重、分開計數，不互相比對。讀到與去掉的筆數都是過濾之後、整個讀檔視窗內的筆數，進資料品質一節，卡上照這個意思標。已知限制：同一車同一秒的進站與離站只會留一筆，採集端用的也是這個鍵，所以這個限制在原始檔就存在，卡上要寫。

### 附屬路線併回路線，按車牌、路線、方向切趟

事件的 `RouteID` 先透過 `GetRoute.gz` 的 `(Id, pathAttributeId)` 對回路線 `Id`，站序取 `GetStop.gz` 中 `routeId` 等於該路線、`goBack` 等於事件 `GoBack` 的那一組，以 `Id` 對 `StopID` 得到 `seqNo`。切趟的分組鍵是 `(BusID, 路線 Id, GoBack)`，不是附屬路線。每趟記下事件最多的那個 `pathAttributeId`，卡上給三條附屬路線各佔多少趟。`StopID` 對不到該方向站序的事件不悄悄丟掉，計入「對不到站序的事件」。

理由：已核對 162347、162348 的站序就是 15373 的整段去程與返程，分開切會把同一種行駛切成三組樣本數更少的統計。這是對這一天的核對結果，不是對 feed 的一般性假設，所以 SQL 在載入靜態資料時要比對每條附屬路線在 `GetPathDetail.gz` 依 `sequenceNo` 排好的 `stopId` 序列，是否等於 `GetStop.gz` 對應方向依 `seqNo` 排好的站序。對應方向取附屬路線的站牌在 `GetStop.gz` 所在的 `goBack`；兩個方向都有時，比的是整條路線的站序，15373 全程就是這種。`sequenceNo` 每條附屬路線各自從 0 起算，所以只比順序，不比值。不等就在資料品質一節標出來並寫出比對的方向，而不是靜默併計。

替代方案：按 `pathAttributeId` 分開切、分開報（樣本更碎，且三組的站序完全相同，分開沒有資訊）。

### 切趟規則：方向改變、站序回頭或中斷超過 60 分鐘就是新的一趟

同一 `(BusID, 路線 Id)` 的事件依 `DataTime` 排序，遇到下列任一情況開新的一趟：`GoBack` 與前一筆不同；`seqNo` 小於前一筆；與前一筆相隔超過 60 分鐘。趟次的起點時刻取第一個觀測到的站牌的離站事件（`CarOnStop` 0），沒有離站事件時取該站的到站時刻並標記 `start_from_arrival`；終點時刻取最後一個觀測到的站牌的到站事件（`CarOnStop` 1），沒有時取離站時刻並標記 `end_from_departure`。

完整性依觀測到的第一個與最後一個 `seqNo` 是否等於該方向的最小與最大 `seqNo` 分為 `complete`、`missing_start`、`missing_end`、`missing_both`。一天版不放寬，先量有多少趟因為漏掉端點而不完整；放寬要等這個數字出來。

60 分鐘是保險：站序回頭已經能切出絕大多數的趟次，中斷規則處理同方向、站序剛好遞增的罕見接續。常數寫在參數檔。

### 折返停留只算同一車牌相鄰兩個完整趟次，最後一趟不算

對每個車牌把趟次依起點時刻排序，折返停留等於下一趟起點時刻減本趟終點時刻，只在兩趟都是 `complete` 且同一路線 `Id` 時成立。不成立的配對分三類計數：有一趟不完整、下一趟是別的路線、差值為負。當天最後一趟沒有折返停留。統計給筆數、p10、p50、p90（分鐘、一位小數、線性內插）、不到 15 分鐘的比例、六個分箱（0 到 5、5 到 10、10 到 15、15 到 30、30 到 60、60 以上），並按結束那趟的方向分列。

### 班次串用第 19 條之 2 的四小時視窗算，重疊的視窗併成一串

對每個車牌，只用相鄰完整趟次串起來的序列（遇到不完整趟次就切斷）。對序列中每一趟 i，找最早的 j 使得第 j 趟終點減第 i 趟起點達 240 分鐘；視窗內的休息額度是第 i 到第 j-1 趟之後、長度達 15 分鐘的折返停留總和；額度不到 30 分鐘的視窗標為不合規。同一車牌、趟次範圍重疊的不合規視窗併成一條班次串。卡上給班次串數、涉及車輛數、每一串的起訖時刻與趟數，不給車牌。

替代方案：定義「相鄰折返停留都不到 15 分鐘的連續趟次」為串再看長度（直觀，但漏掉幾段 20 分鐘加起來仍不到 30 分鐘的情況，與法條不符）。

### 載客剖面用離站時的車上人數，時段分四段

每趟以同一 `BusID`、同一路線 `Id` 與 `GoBack`、`DataTime` 落在趟次起訖之間的 `bus_seat_event` 記錄接上，每站取離站記錄的 `RemainingNum`，沒有離站記錄時取到站記錄。淨上下車等於本站值減前一個有值的站，兩站 `seqNo` 相差大於 1 時標記跨站。時段依趟次起點小時分四段：07 到 09 早尖峰、09 到 17 日間、17 到 19 晚尖峰、其餘；邊界含起不含迄。剖面表按方向、時段、`seqNo` 給趟數、中位數、p90，站名取 `GetStop.gz` 的 `nameZh`。

歸零檢查的取值見下一個決定。另計負值筆數與相鄰觀測站跳動超過 30 的筆數。涵蓋率：有至少一筆車上人數的趟次比例、有值的趟次站比例。

替代方案：直接用 `bus_seat_event` 自己切趟（兩套趟次定義會分歧，否決）。

### 歸零檢查看起站上客前與末站下客後的記錄

每個完整趟次取兩個值。起站上客前：同一 `BusID`、同一路線 `Id` 與 `GoBack`、站牌對到該方向起站 `seqNo` 的到站記錄（`CarOnStop` 1），`DataTime` 不晚於趟次起點、不早於起點前 60 分鐘，取最後一筆的 `RemainingNum`。末站下客後：同樣條件、站牌對到末站 `seqNo` 的離站記錄（`CarOnStop` 0），`DataTime` 不早於趟次終點、不晚於終點後 60 分鐘，取第一筆。每個方向的每一端各報一列，標出那一端的站名：有記錄的趟數、沒有記錄的趟數（該方向的完整趟次減有記錄的趟數）、等於 0 的比例、不超過 2 的比例、最大值；比例只算有記錄的趟次。這兩筆記錄只用在歸零檢查，不接進載客剖面與淨上下車，剖面仍以趟次起訖為界。

這取代任務 5.2 實作的取值。原本取趟次起訖之間、每站離站優先的值，起站拿到的是上完客之後、末站拿到的是下客之前的人數。2026-10-19 的卡上兩端各只有 0.9% 等於 0（起站 116 趟、末站 117 趟，量到的），不管系統有沒有歸零都會是這種結果，回答不了 Open Questions 的第二題。系統若在趟次之間歸零，起站上客前與末站下客後是最可能看到 0 的兩個時刻。

60 分鐘是估計值，依據是切趟的中斷門檻也是 60 分鐘：離趟次起訖超過一個中斷門檻的記錄，已經不能確定跟這一趟連在一起。卡上每一端「沒有記錄的趟數」會量出這個視窗夠不夠；同秒的到離站只留一筆的去重限制，也可能讓某些趟次在這兩個時刻沒有記錄。常數寫在參數檔。

替代方案：保留原本的取值（答不了問題）；看同一車牌上一趟末站到站與下一趟起站離站的差（混進上下客，分不出歸零）；把趟次起訖延伸到包含這兩筆（會改動折返停留與趟次時間這些已經驗過的定義）。

按方向分列，是因為兩端的性質不同，合在一起會互相掩蓋。2026-10-19 的真資料（量到的）：天母那端折返停留的中位數是 16.2 分鐘，車在那裡真的停下；青年公園那端只有 1.9 分鐘，車從青年公園(馬場町)幾乎馬上從青年社宅出發，那一端的人數可能含沒有下車的乘客。拆開來看，去程起站職能發展學院二上客前 48 趟、中位數 6 人、2.1% 等於 0，是最能回答歸零問題的一列；末站下客後 66 趟裡有 63 趟來自青年公園那端。合成「起站」「末站」兩列時，這些差異都看不到。

### 每個方向數末站在終點後有沒有離站事件

資料品質一節按方向報兩個數：完整趟次數，以及其中末站在終點後有離站事件的趟數。離站事件取 `bus_event` 去重後的事件：同一 `BusID`、同一路線 `Id` 與 `GoBack`、站牌對到該方向末站 `seqNo`、`CarOnStop` 0、`DataTime` 不早於趟次終點且不晚於終點後 60 分鐘（與歸零檢查同一個常數）。

理由：2026-10-19 的真資料（量到的）裡，去程的末站青年公園(馬場町) 63 趟完整趟次都有離站事件，返程的末站職能發展學院二（站牌 `Id` 16738）61 趟只有 3 趟有。缺的 58 趟在終點後 60 分鐘內兩支 feed 都有其他事件，但沒有那一站的離站；其中 57 趟在終點後（中位數 1.9 分鐘）多一筆同一站的到站事件，56 趟的車上人數跟第一筆相同，是重報不是下客；之後車以去程起站（站牌 `Id` 16648，同名職能發展學院二）的身分出發。這是 feed 在那個端點的行為，不是讀檔或視窗的問題，歸零檢查的末站下客後在那一端因此量不到。卡上要有這個數字，讀者才知道哪一列的「沒有記錄」來自 feed 本身。

這只量事件存不存在，不改切趟與趟次終點的定義；重複到站的筆數與它跟去程起站的關係不在這個 change 量。

替代方案：在卡上寫死「返程末站沒有離站事件」的文字（換一天、換一條路線就可能不對，數字才會跟著資料變）；改用終點後重複的那筆到站記錄當末站下客後（實測人數跟第一筆相同，不是下客後的值）。

### 去程半與反程半看是不是那台車當天的第一趟或最後一趟

同一 `BusID`、同一路線 `Id`、起點落在台北日 D 的趟次，依起點時刻排序，最早的是那台車當天的第一趟、最晚的是最後一趟；當天只有一趟時兩者都算。不分完整性，所有趟次都算。資料品質一節的附屬路線表加兩欄：各附屬路線的趟次中，有幾趟是第一趟、幾趟是最後一趟。

理由：2026-10-19 的 `trips.csv` 裡，162347 的 9 趟都是那台車當天在這條路線的最後一趟，162348 的 10 趟有 9 趟是第一趟（量到的），看起來是出車與收車時跑的單程。這只在檢查用的 CSV 裡，Open Questions 的第三題要求答案留在卡上。「當天」只看這條路線：同一台車跑別的路線的趟次不在讀檔範圍內，卡上的說明要寫明。

替代方案：按時段分列附屬路線的趟數（看得到幾點掛，看不出跟出車、收車的關係）；只放在 `trips.csv`（不在卡上，答不了第三題）。

### 卡只出路線層級彙總，逐趟明細另存 tmp

Markdown 卡不含任何 `BusID`，測試用車牌樣式的正規表達式掃整份輸出。逐趟、逐折返、逐站的 CSV 寫到 `--inspect-dir`，預設 `tmp/health-card/<路線 Id>-<台北日>/`，在 `.gitignore` 的 `/tmp/*` 之下。卡預設寫到標準輸出，`--out` 指定檔案；跑出來的一天版放 `docs/cards/15373-2026-10-19.md`。

### 常數集中在 analysis/params.sql

往前回看的時數（中斷門檻的兩倍、以小時無條件進位，目前是兩小時）、兩小時溢出、60 分鐘中斷、15 分鐘短停留、240 分鐘視窗、15 分鐘休息下限、30 分鐘休息額度、四個時段的小時邊界、跳動 30 人、歸零檢查往趟次起訖外找記錄的 60 分鐘，全部以變數定義在 `analysis/params.sql`，SQL 其他檔案只引用變數。改定義只改一個檔。

### 測試用合成 fixture，DuckDB CLI 不在時整組明確略過

`spec/fixtures/analysis/` 放一組假的原始檔：假車牌（`TEST-0001` 這類）、假路線 9001 與附屬路線 9001、9002、9003、每方向 5 站的 `GetRoute.gz`、`GetStop.gz`、`GetPathDetail.gz`（外層照真資料包 `EssentialInfo` 與 `BusInfo`，另有一條對照路線 9100），以及涵蓋完整趟、漏起站、漏末站、跨午夜、前一晚發車與終點站停留跨午夜、換附屬路線、同方向中斷、跨小時檔重複、歸零異常、起站上客前與末站下客後的記錄的 `bus_event` 與 `bus_seat_event` 小時檔，含讀檔視窗外不該被讀的 2026-10-18 的 21 時檔與 2026-10-20 的 02 時檔。RSpec 放 `spec/analysis/`，只載入 `spec_helper`，不載入 Rails；用 `spec/support/duckdb.rb` 的 helper 執行 `bin/health-card` 或單獨的 SQL 階段並讀回結果。`duckdb` 不在 PATH 時整組以明確訊息略過，訊息寫出安裝方式。不動 `bin/ci`。

`spec/analysis/` 測的是 SQL、fixture 與執行檔，沒有 Ruby 類別可以 describe，所以 `.rubocop.yml` 對這個目錄關掉 `RSpec/DescribeClass`，用 `inherit_mode` 合併 `Exclude`，保留 rubocop-rspec 原本對 requests、system 等目錄的排除。

替代方案：用 2026-10-19 真資料的片段當 fixture（含真車牌，違反不釋出單一車牌時間軸的原則，而且無法刻意涵蓋邊界案例）。

## Implementation Contract

**行為**：操作者在 website repo 執行

```
bin/health-card --data <原始檔根目錄> --route 15373 --day 2026-10-19 [--static-day 2026-10-19] [--out docs/cards/15373-2026-10-19.md] [--inspect-dir tmp/health-card/15373-2026-10-19]
```

得到一份 Markdown 卡（標準輸出或 `--out`）與一個目錄的 CSV。`--data` 省略時讀環境變數 `TURNAROUND_DATA`；`--static-day` 省略時等於 `--day`。

**介面與資料形狀**：

- 輸入目錄結構：`<data>/bus_event/<台北日>/<HH>.jsonl` 或 `.jsonl.gz`、`<data>/bus_seat_event/...` 同、`<data>/static/<台北日>/GetRoute.gz`、`GetStop.gz`、`GetPathDetail.gz`。算 D 時兩支 feed 都讀 D-1 的 22、23 時、D 全部、D+1 的 00、01 時，沒有檔的小時略過。
- `analysis/params.sql`、`analysis/10_load.sql`、`analysis/20_trips.sql`、`analysis/30_layovers.sql`、`analysis/40_load_profile.sql`、`analysis/50_quality.sql`、`analysis/60_export.sql`：`params.sql` 先執行，其後的編號階段檔依檔名順序串接；每個階段建立同名的 table 或 view，後面的階段只引用前面的名字。`analysis/README.md` 說明用法與各階段產出。
- 檢查目錄 CSV：`trips.csv`（bus_id、route_id、path_attribute_id、go_back、start_time、end_time、first_seq、last_seq、n_events、n_stops_observed、completeness、start_from_arrival、end_from_departure）、`layovers.csv`、`chains.csv`、`profile.csv`、`quality.csv`。
- Markdown 卡的節與順序：標題列（路線名、起迄、附屬路線名稱與 `pathAttributeId`、資料日、靜態快照日、產出時刻）、資料品質、趟次、折返停留、載客剖面、資料限制、資料來源與授權。資料限制與顯名聲明是固定文字，顯名聲明逐字取 `docs/data-sources.md`「授權」一節的三段。
- `.rubocop.yml`：對 `spec/analysis/**/*` 關掉 `RSpec/DescribeClass`，`inherit_mode` 合併 `Exclude`。

**失敗模式**：

- 缺參數或日期格式錯：印用法到標準錯誤，結束碼 1。
- `duckdb` 不在 PATH：印「需要 DuckDB CLI，`brew install duckdb`」，結束碼 2。
- 該台北日沒有任何 `bus_event` 檔，或 `static/<靜態快照日>/` 不存在：印缺什麼、列出有哪些快照日，結束碼 3；不自動改用別的快照日。
- `duckdb` 回非零：把它的標準錯誤原樣印出，結束碼 4。
- 上面四種情況都不寫任何輸出檔。
- D-1 或 D+1 沒有檔不算失敗，照常執行。

**驗收**：

- `bundle exec rspec spec/analysis` 在裝了 DuckDB CLI 的機器上全綠；沒裝時每個 example 顯示略過原因。
- 對 fixture 跑 `bin/health-card`，`trips.csv` 的趟次數、完整性標記、`layovers.csv` 的分鐘數、`chains.csv` 的串數與 spec 的 Example 一致。
- 對 2026-10-19 真資料跑一次，產出 `docs/cards/15373-2026-10-19.md`，卡裡沒有任何符合車牌樣式的字串，六個節都在；載客剖面一節的歸零表按方向各有起站上客前與末站下客後兩列並標站名，資料品質一節的附屬路線表有當天第一趟與最後一趟兩欄，並有每個方向末站在終點後有離站事件的趟數。
- `bin/rubocop bin/health-card spec/analysis spec/support/duckdb.rb` 無警告。

**範圍邊界**：在範圍內的是上面列的檔案與行為。不在範圍內：Rails、資料庫、排程、其他路線的核對、`bin/ci` 與 `bin/setup`、n-gear、任何文件裡的結論。

## Risks / Trade-offs

- [DuckDB 版本或 table function 不吃 `getvariable()`] → 任務 1.1 已在 1.5.6 確認可行；版本需求 1.1 以上寫在 `analysis/README.md`。
- [JSON 型別推斷在不同小時檔之間不一致，例如 `RemainingNum` 全空的檔被推成 VARCHAR] → `read_json` 明確給 `columns`，不靠 auto。
- [`read_json` 拿到空的檔案清單會直接報錯] → D 沒有 `bus_event` 檔時由執行檔先擋下，結束碼 3；`bus_seat_event` 整個視窗都沒有檔時 DuckDB 報錯，依失敗模式以結束碼 4 原樣透傳。
- [終點站事件漏得比預期多，完整趟次比例很低] → 這正是一天版要量的數字；不在這個 change 放寬定義，放寬留給下一個 change 帶著數字決定。
- [同秒的進站與離站只留一筆] → 採集端的鍵就是 `(BusID, DataTime)`，無法在下游補回；卡的資料限制寫明。
- [去程半、反程半併回整段只在 2026-10-19 核對過] → SQL 每次跑都比對站序，不等就標在資料品質一節。
- [一天的樣本太少，離峰時段一個方向只有幾趟] → 卡的標題與資料限制都寫「一天版，驗定義用，不可引用」。
- [測試在沒有 DuckDB 的機器上整組略過，CI 可能一直綠] → 略過訊息明確；要不要讓 `bin/ci` 強制要求 DuckDB 另開 change。
- [1.5 百萬筆到離站事件加同量車上人數，筆電記憶體] → 讀檔時先以 `RouteID` 過濾成三條附屬路線，再做其餘計算。
