## Context

路線頁的每一塊都從 `RoutePage::Coverage#route_days` 拿日子：`range=day` 是選的那一天，`range=7d` 是那一天和前 6 個台北日裡已寫入的日子（決策「路線頁的網址、日期與範圍」，zhongshan-route-page）。`RouteCoverageComponent` 列出涵蓋的日期與星期（`ApplicationComponent#day_label`，例如「2026-10-19（一）」），只有在 7d 才加一句「沒有分平日與假日」；資料限制元件的 `items` 也有同一句。首頁 `HomePage::RouteList` 用一次 `DISTINCT ON` 查詢取每條路線最新一天的 `route_days.*`，卡上用同一個 `day_label`。

已核對的事實（2026-10-23）：

- 衍生表只有 15373 的 2026-10-19、10-20、10-21，全是平日；10-22 的讀檔視窗已經結束，還沒載入。
- 辦公日曆是 data.gov.tw/dataset/14718（行政院人事行政總處，政府資料開放授權條款第 1 版，每年一份）。每份檔案的網址都不一樣，路徑裡有一串 UUID：115 年那份是 2025-06 上架的，116 年那份是 2026-07 上架的；114 年另外有一份「(1141020 更新)」，表示日曆會在年中改版。
- 115 與 116 年兩份都是 UTF-8 帶 BOM、CRLF 換行、365 列（量到的）：
  - 表頭是 `西元日期,星期,是否放假,備註`，日期格式是 `20261026`，星期是「一」這樣的一個字。
  - 「是否放假」只有 0 與 2，備註裡沒有逗號。
  - 2026 年有 120 個假日，其中 10-24（六）、10-25（日，臺灣光復暨金門古寧頭大捷紀念日）、10-26（一，補假）；2027 年有 121 個。兩年都沒有補班日。
  - 下載不經過轉址，HTTP 200。
- 公運處的班表分不出國定假日：中山幹線在 `GetSemiTimeTable.gz` 的 `DateValue` 1 與 7 只有一段 05:30 到 21:00、班距 15 到 20 分鐘；2 到 6 在 06:30 到 08:00 與 16:00 到 17:30 是 4 到 6 分鐘（2026-10-22 快照，量到的）。`GetTimeTable.gz` 的 `DateType` 全是 0。
- 捷運出入口快照的做法：
  - `MrtExitsSnapshot` 用一個可以替換的 fetcher 下載（預設是類別裡的 `HTTP_FETCHER` lambda，最多跟三次轉址），檢查通過才寫 `external/taipei-mrt-exits/<台北日>.csv`，寫檔時先寫暫存檔再改名。
  - `RouteDayLoader#newest_mrt_exits` 取檔名日期最新的那一份，找不到就丟出「沒有捷運出入口快照：先跑 bin/rails external:mrt_exits」，用到的日期存進 `route_days.mrt_exits_day`。
  - 那個欄位可以為空，因為 migration 不回填（`AddMrtOverlapToDerivedTables` 的註解）。
- 20 個 spec 檔各自用 `RouteDay.create!` 建路線日，`spec/models/route_day_spec.rb` 用 `described_class.create!`。Gemfile 已經有 `factory_bot_rails`，`spec/support/factory_bot.rb` 也 include 了它的語法，但還沒有任何 factory。
- Gemfile 沒有 `csv`；出入口快照用逗號切欄，切不出剛好的欄數就拒絕。

詞彙依 `docs/spectra/LANGUAGE.md`：日型別、台北日、路線頁、首頁、衍生表、資料限制、顯名聲明、趟次。這個 change 會改寫「日型別」那一條。

## Goals / Non-Goals

**Goals:**

- 每一個寫進衍生表的台北日，都帶著照辦公日曆分出來的日型別，以及用到哪一份日曆。
- 路線頁的範圍不再把平日與假日混在一起，涵蓋的日子看得出是哪一類，一個連結就能跳到另一類。
- 首頁與路線頁不再讓補假的週一看起來像平日。
- 「辦公日曆的假日」等於「公車跑假日班距的日子」這個假設，有明確的驗證方法與查詢，記在詞彙表的待確認，交件後照著補驗。

**Non-Goals:**

- 颱風停班日、補班日與連假另外分類。
- 班表對照，包括 `DateValue` 與業者機動預排班表。
- 最近一個月與月卡、Markdown 健檢卡。
- 首頁放指標，或改首頁資料來源那一塊的三個連結。
- 修改任何指標的定義；其他路線；排程與部署。
- 交件前用真資料驗證補假日的班距：活動 2026-10-24 交件，10-26 的資料 2026-10-27 02:00 才有（見「用 10-26 的發車數驗證補假日跑的是假日班距」）。

## Decisions

### 日型別照辦公日曆的「是否放假」分兩類：0 是平日、2 是假日

一個台北日的日型別，看那一年辦公日曆裡那一天的「是否放假」：0 是平日（`weekday`），2 是假日（`holiday`）。`備註` 不是空字串時一起存，例如 10-26 的「補假」。補班日在日曆裡本來就標 0，所以算平日，跟詞彙表「補班的週六不是假日」一致；補假標 2，算假日。趟次歸發車那一天（trip-reconstruction 的跨午夜規則），所以 10-26 23:00 發車、10-27 00:30 到站的那趟，帶的是 10-26 的假日。

理由：辦公日曆是台灣通用的放假依據，一年一個檔，而且已經抓得到。公運處自己的班表只分星期幾，分不出國定假日與補假。

替代方案：
- 用星期幾分（10-26 會被當成平日，否決）。
- 用 `GetSemiTimeTable.gz` 的 `DateValue`（只有星期幾，原因同上，否決）。
- 補班日、連假另外分類：2026 與 2027 都沒有補班日，現在的問題用兩類就答得出來，否決。

### 辦公日曆快照按年份存在資料根目錄，算的時候用那一年最新的一份並記下日期

`bin/rails external:office_calendar YEAR=<年>` 把日曆存成 `<TURNAROUND_DATA>/external/office-calendar/<年>/<下載那天的台北日>.csv`；同一天重下載就覆蓋。`derived:load` 算某一天時，用那一天所在年份的資料夾裡檔名日期最新的一份，把那份的日期存進 `route_days.office_calendar_day`。

理由：照決策「出入口快照：下載時轉成 UTF-8，算的時候用最新的一份並記下日期」（zhongshan-mrt-overlap），`derived:load` 的輸入全部放在資料根目錄。日曆會年中改版（114 年有一份「(1141020 更新)」），所以要記下用的是哪一份。改版的日曆是另一個檔案、另一個網址：先把 `DOWNLOAD_URLS` 裡那一年換成新網址，再下載、重跑受影響的日子；只重跑下載會抓回舊版，存成新的日期。按年份分資料夾，是因為一份日曆只涵蓋一年。

替代方案：
- 把 CSV 放進 repo（`derived:load` 的輸入就會一半在資料根目錄、一半在 repo，日曆改版還要 commit，否決）。
- 每次 `derived:load` 都下載（算一天就要連網路，同一天重算還可能拿到不同版本，否決）。

### 每年的下載網址寫成程式裡的常數

`OfficeCalendarSnapshot::DOWNLOAD_URLS` 是年份對網址的對應表，目前有 2026 與 2027 兩年，照 data.gov.tw 上的連結原樣抄錄。`YEAR` 不給時用今天的台北日所在的年份；表裡沒有的年份直接失敗，訊息列出有網址的年份。

理由：每份檔案的網址都帶一串 UUID，沒有固定的「最新一份」網址。寫成常數可以在 review 時看到網址從哪裡來；多一年就加一行。

替代方案：
- 從 data.gov.tw 的資料集 API 依名稱找檔案（資源名稱會變，例如「(1141020 更新)」「_utf8bom」「_Google 行事曆專用」，比對很脆弱，否決）。
- 用 `URL=` 環境變數臨時給網址（操作者每次都要去抄一串 UUID，而且網址不會留在任何地方，否決）。

### 下載時檢查整年的日期、星期與代碼，存成 UTF-8、不帶 BOM、LF 換行

下載回來的內容去掉開頭的 BOM 後，必須是合法的 UTF-8，並通過以下檢查：

- 第一行正好是 `西元日期,星期,是否放假,備註`。
- 資料列數等於那一年的天數。
- 第 n 列的日期是那一年的第 n 天（`YYYYMMDD`）。
- 星期欄等於那個日期的星期（日、一……六）。
- 「是否放假」是 0 或 2。
- 每一列用逗號切出剛好 4 欄。

任何一項不通過就不寫檔，訊息指出哪一行、哪裡不對，既有的快照保持原樣。寫出的檔案跟原檔的列一模一樣，只拿掉 BOM、把 CRLF 換成 LF；先寫暫存檔再改名。成功時印出檔案路徑、天數與假日數，例如「…/2026/2026-10-23.csv：365 天，假日 120 天」。

理由：日曆一年只有 365 列，整份檢查很便宜，而且能擋下抓錯年份或抓到「Google 行事曆專用」那種格式的檔案。之後讀它的程式不用再處理 BOM 與 CRLF。

替代方案：用 `csv` 函式庫解析（Gemfile 沒有 `csv`，而且這份檔沒有引號與欄內逗號；照出入口快照的做法，切不出 4 欄就拒絕，不猜，否決）。

### 下載器從出入口快照抽出來共用

`MrtExitsSnapshot::HTTP_FETCHER` 搬到 `HttpFetcher` 模組。它有一個 `call(url)` 方法，回傳 `[HTTP 狀態碼, 內容位元組]`，最多跟三次轉址。兩個快照類別都用它當預設的 fetcher；測試照舊傳自己的 lambda，不連網路。

理由：兩個類別要的是同一件事。抽出來之後，出入口快照的行為不變，它的 spec 不用改。

替代方案：
- 在日曆類別裡複製一份（兩份要一起維護，否決）。
- 直接引用 `MrtExitsSnapshot::HTTP_FETCHER`（日曆跟捷運扯在一起，否決）。

### 日型別在 derived:load 時由 Ruby 寫進 route_days，不經過 DuckDB

`route_days` 加三欄：`day_type`（字串，`weekday` 或 `holiday`）、`day_note`（字串，可以為空）、`office_calendar_day`（日期）。`day_type` 跟其他類別欄位（`completeness`、`band`）一樣用字串，不加 CHECK 約束，也不用 Rails enum，因為唯一的寫入者是 loader，它只會寫出這兩個值。`RouteDayLoader` 在找完捷運出入口快照之後、跑 DuckDB 之前，用 `OfficeCalendarSnapshot.entry(data_root:, day:)` 查那一天，再在同一個交易裡把三個值跟路線日一起寫入。查不到就丟出 `RouteDayLoader::Error`，`DerivedLoadCommand` 照現有的方式印成「<日期> 失敗：<原因>」，那一天什麼都不寫。

理由：日型別不改變任何算出來的值，只是一天的標籤。由 Ruby 寫，`analysis/` 的 SQL 與 `bin/health-card` 都不用動。先查捷運快照、再查日曆，兩份都缺時訊息仍然先講捷運，既有的 example 不會變。日曆查詢放在 `OfficeCalendarSnapshot`，日曆格式的知識（表頭、代碼對應）只在一個類別裡。

替代方案：
- 另開一張日曆表，讀頁面時再 join（日曆改版不用重載，但頁面得處理「這一天還沒有類型」，也跟出入口快照的做法不一致，否決）。
- 當成 DuckDB 變數傳進 `derived_export.sql`，寫進 `route_day.csv`（為了一個標籤繞過 SQL 和 health card 共用的那條路，否決）。

### 日型別必填：先加可以為空的欄位，重載之後再改成必填

分兩個 migration：

- 第一個加三個可以為空的欄位，loader 從這時起就會寫入。
- 第二個把 `day_type` 與 `office_calendar_day` 改成 NOT NULL；`day_note` 照舊可以為空。執行前它先檢查有沒有還沒帶日型別的路線日；有的話就丟出錯誤，列出那些路線與日期，以及要先跑的 `external:office_calendar` 與 `derived:load`，不改 schema。

中間那一步是把已寫入的日子重跑一次 `derived:load`。

理由：每一個存進去的日子都要有類型，路線頁的範圍才篩得了；要在資料庫層面保證這件事，就得是 NOT NULL。現有的資料列沒辦法在 migration 裡回填，因為 migration 讀不到資料根目錄。先加欄位、重載、再改成必填，每一步結束時測試都是綠的。

替代方案：
- 像 `mrt_exits_day` 那樣永遠可以為空，頁面顯示「要重新載入」（範圍篩選要多處理一種「沒有類型」的狀態，而且這個狀態會一直留在產品裡，否決）。
- 一個 migration 先刪掉所有衍生表的資料，再加必填欄位（衍生資料雖然可以重算，但 migration 默默刪資料會嚇到人，否決）。

### 測試改用 route_day factory 建路線日

新增 `spec/factories/route_days.rb`，預設值跟現有 spec helper 的一樣：路線 9001、2026-10-19、測試幹線、甲站、戊站、`static_day` 等於 `day`、`loaded_at` 是現在。再加上 `day_type` 預設 `weekday` 與 `office_calendar_day` 2026-10-19。21 個檔裡建路線日的地方改成 `create(:route_day, ...)`，只傳各自不同的欄位；每個 spec 的斷言都不改。需要假日的測試明確傳 `day_type: "holiday"`。

理由：日型別必填之後，21 個檔都得補值。改成 factory 只要補一次，`route_days` 以後再加欄位也只改一處。`factory_bot_rails` 已經在 Gemfile 裡，AGENTS.md 也寫明測試用 FactoryBot。

替代方案：在 21 個檔的 `create!` 各補兩個欄位（工作量一樣，重複的地方還在，否決）。factory 依日期查 fixture 日曆自動決定類型（測試資料就綁上查詢程式，一個 bug 會讓整套測試一起出錯，否決）。

### 路線頁的網址、日期與範圍：最近 7 天只留跟選的那一天同類型的日子

**Supersedes**: zhongshan-route-page / 路線頁的網址、日期與範圍

規則：

- `GET /routes/:route_id`，參數有 `day`（`YYYY-MM-DD`，台北日）、`range`（`day` 或 `7d`）與 `buffer`（`buffer-trade`）。
- 沒給 `day` 時，用這條路線已寫入的最新一天；沒給 `range` 時是 `day`。
- `range=day` 涵蓋選的那一天。`range=7d` 涵蓋選的那一天，加上它之前 6 個台北日裡已寫入、而且日型別跟選的那一天相同的日子。
- 頁面標出涵蓋的日子是平日還是假日，並列出每一天的日期、星期與備註。
- 路線不在設定的路線清單裡回 404；在清單裡、但那一天沒有資料時回 200，顯示這一天還沒有資料，並列出有資料的日期。
- 頁面不出現車牌。
- 頁面有哪些區塊、什麼順序，以 `route-page` 規格的 Page content 為準。

這次只改 7d：原本涵蓋那 7 個台北日裡所有已寫入的日子，並寫明沒有分日型別。

理由：2026-10-23 討論時由使用者選定。不加網址參數；選的那一天是哪一類，涵蓋的就是哪一類，網址狀態只有 `day` 與 `range` 兩個。之後把天數改成 30 天，沿用同一條規則。

替代方案：
- 加 `day_type` 參數切換平日與假日（多一種網址狀態，當天模式下這個參數要怎麼處理還得另外定，否決）。
- 往前數 7 個同類型、有資料的日子（7 個假日會橫跨大約三週，「最近 7 天」這個名字也得跟著改，否決）。

### 跳到另一類的連結找選的那一天以前最近的另一類日子

涵蓋的日子下方放一個連結，跳到「選的那一天以前（含）最近一個已寫入、日型別不同的日子」。範圍跟現在一樣、不帶 `buffer`，跟範圍切換的連結一致。文案如下：

- 7d：「看平日 → 2026-10-23（五）為止的最近 7 天」。
- 當天：「看平日 → 2026-10-23（五）」。
- 往假日的方向就寫「看假日」。

找不到這樣的日子就不放連結。

理由：翻到舊的日子時，讀的人看的是那段時間；如果跳到全部資料裡最新的另一類日子，就會被帶離那段時間。

替代方案：跳到全部資料裡最新的另一類日子（理由如上，否決）；首頁與路線頁都加平日／假日的切換按鈕（等於多一個網址參數，否決，見上一條）。

### 平日與假日的顯示名稱放共用的 locale

`config/locales/tw.yml` 與 `en.yml` 加 `day_types.weekday`（平日、weekday）與 `day_types.holiday`（假日、holiday），由 `ApplicationComponent#day_type_label(day_type)` 提供給路線頁與首頁的元件。其他文案照舊放在各元件同層的 `.yml`：

- 路線頁：「涵蓋的日子（%{day_type}）」與「看%{day_type} → …」。
- 首頁：「最新資料 %{day}%{day_type}」，例如「最新資料 2026-10-20（二）平日」。

理由：同一組詞兩個元件都要用，各元件的 `.yml` 不共享。做法跟 `day_label` 上提到 `ApplicationComponent`（home-page）一樣。

### 顯名聲明加一行辦公日曆

`AttributionComponent` 在北捷那一行之後加一行：「行政院人事行政總處 中華民國政府行政機關辦公日曆表（data.gov.tw/dataset/14718），依政府資料開放授權條款第 1 版釋出」。en 用同一段原文，照北捷那一行的做法。

理由：頁面會顯示日曆的備註（例如「補假」、節日名稱），也用日曆決定哪些日子放在一起算，這就是在利用這份資料。授權條款第三條規定，沒有盡到顯名義務，視為自始未取得授權。

### 颱風停班日照日曆算，寫進資料限制

路線頁資料限制 `items` 裡「涵蓋的日子沒有分平日與假日。」那一條，改成：「平日與假日照人事行政總處的辦公日曆分；颱風停班不在日曆裡，那幾天照日曆算。」en 對應改寫。首頁的 `home_items` 四條不變。

理由：辦公日曆是前一年就公布的年曆，颱風停班是當天才由縣市政府宣布的。第一張月卡是 11 月那張，11 月以後很少有颱風；真的碰到時，再加一份人工維護的例外清單，到時候另開 change。

### 用 10-26 的發車數驗證補假日跑的是假日班距

**2026-10-23 改成交件後補驗**：活動 2026-10-24（六）交件。10-26 的讀檔視窗要到 10-27 02:00 才結束，連第一個假日 10-24 也要到 10-25 02:00 才算得出來，交件前資料庫裡不會有任何假日。使用者選定先收尾：這個 change 的驗收不含這項驗證，下面的方法與判準照舊，改記在詞彙表「日型別」的邊界當作待確認，交件後照著做。

10-26 的讀檔視窗在 10-27 02:00 結束，之後載入 15373 的 10-19 到 10-26。驗證方式：

- 對每一天、每個方向，數一整天的趟次：`trips` 裡那一天、那個方向的每一列，完整與不完整的都算。
- 平日實測（10-19 到 10-22，2026-10-23 查詢，量到的）：去程 82、90、86、83 趟，返程 81、89、82、81 趟。假日照分時段班距估計（不是量到的）：05:30 到 21:00 共 15.5 小時，每 15 到 20 分鐘一班是 47 到 62 趟，再加 21:00 以後的少數定時班次。
- 平日的參考值是 10-19 到 10-23 的平均，假日的參考值是 10-24 與 10-25 的平均。
- 兩個方向都要符合：10-26 的趟數離假日的參考值比離平日的近。

結果符合，就把六個數字（每個方向的平日參考值、假日參考值與 10-26 的趟數）與結論寫進詞彙表「日型別」的邊界，並拿掉那條待確認；不符合就向使用者回報，另開 change 修正分法，在那之前 10-26 在頁面上被標成假日。

查詢（開發資料庫）：

```sql
SELECT rd.day, rd.day_type, t.go_back, count(*) AS trips
FROM trips t JOIN route_days rd ON rd.id = t.route_day_id
WHERE rd.route_id = 15373 AND rd.day BETWEEN '2026-10-19' AND '2026-10-26'
GROUP BY rd.day, rd.day_type, t.go_back
ORDER BY rd.day, t.go_back;
```

理由：辦公日曆是機關上班的日曆，不是公車的營運日曆。原本比的是 06:30 到 08:00 的發車數，但 2026-10-23 用 10-19 到 10-22 實測（量到的），平日去程只有 6 到 9 趟、返程 3 到 5 趟，遠低於照班距估的 15 到 22 趟，返程更跟假日的估計（4 到 6 趟）重疊，一天的資料分不出來。一整天的趟數大了一個數量級，平日四天都落在 81 到 90 之間，跟假日的估計明顯分開。2026-10-23 由使用者選定改用一整天的趟數。

交件前查到的間接證據（2026-10-23）：業者機動預排班表（`GetSpecTimeTable.gz`，2026-10-23 的快照）只排到 10-25，沒有 10-26，也沒有中山幹線的條目；公運處過去春節連假的原則是「一般路線依假日班次行駛」（例如 2020 年的報導），講的不是補假日。兩者都支持這個假設，但不能代替實測。

## Implementation Contract

**行為**：

- 操作者執行 `bin/rails external:office_calendar YEAR=2026`（`TURNAROUND_DATA` 指到資料根目錄），得到 `external/office-calendar/2026/<今天的台北日>.csv`，並看到「<路徑>：365 天，假日 120 天」。
- 執行 `bin/rails derived:load ROUTE=15373 FROM=2026-10-19 TO=2026-10-26`（10-27 02:00 之後）。每天照舊印出寫入的筆數，存進去的路線日帶著日型別：10-24、10-25、10-26 是假日，10-26 的備註是「補假」，其餘是平日。
- `/routes/15373?day=2026-10-26&range=7d`：
  - 涵蓋 10-24、10-25、10-26，標成假日，10-26 帶著「補假」。
  - 有一個連結「看平日 → 2026-10-23（五）為止的最近 7 天」，指向 `/routes/15373?day=2026-10-23&range=7d`。
  - 那一頁涵蓋 10-19 到 10-23，標成平日，沒有往假日的連結，因為 10-23 以前沒有已寫入的假日。
- 沒帶參數的 `/routes/15373` 顯示最新一天，例如 10-26：「涵蓋的日子（假日）：2026-10-26（一）補假」。
- 首頁 15373 那張卡寫「最新資料 2026-10-26（一）假日」。
- 每一頁的顯名聲明多了辦公日曆那一行。

交件前資料庫裡只有平日。上面跟 10-24 到 10-26 有關的行為，由 request 與 component 測試用測試資料驗證；真資料上的這幾頁，跟 10-26 的驗證一起在交件後補看。

**介面與資料形狀**：

- `OfficeCalendarSnapshot`：
  - 常數：`DOWNLOAD_URLS`（年份對網址）、`HEADER`、`DIRECTORY = "external/office-calendar"`，以及代碼對日型別 `{"0" => "weekday", "2" => "holiday"}`。
  - `.run(env, out:, fetcher:, day:)` 回傳結束碼，讀 `TURNAROUND_DATA` 與 `YEAR`。
  - 實例接資料根目錄、年份、下載那天與 fetcher；`#path` 是那一份的路徑；`#call` 寫檔並回傳天數與假日數。
  - `.entry(data_root:, day:)` 回傳 `Entry`，帶 `day_type`、`note`（沒有備註時是 nil）與 `snapshot_day`。
- `HttpFetcher.call(url)` 回傳 `[狀態碼, 內容位元組]`，`MrtExitsSnapshot` 改用它當預設的 fetcher。
- `route_days`：`day_type` 字串 NOT NULL（`weekday` 或 `holiday`）、`day_note` 字串可以為空、`office_calendar_day` 日期 NOT NULL。
- `RoutePage::Coverage`：
  - `#day_type` 是選的那一天的日型別；那一天沒有資料時是 nil。
  - `#other_type_day` 是另一類連結要跳去的日子，沒有就是 nil。
  - `#route_days` 在 7d 時只回同類型的日子。
  - 已寫入的日子與它們的類型用同一次查詢取得。
- `RouteCoverageComponent`：涵蓋的日子那一行帶 `data-day-type`，每個日子照舊用 `data-day`；另一類的連結帶 `data-other-day-type`，值是連結指向的那一類。
- `ApplicationComponent#day_type_label(day_type)` 回傳平日或假日。

**失敗模式**：

- `external:office_calendar`：以下情況都印出原因、結束碼非零、不寫檔，既有快照不變：
  - 沒有 `TURNAROUND_DATA`。
  - `YEAR` 不是四位數字，或者表裡沒有那一年；訊息列出有網址的年份。
  - HTTP 不是 200。
  - 內容不是 UTF-8。
  - 表頭不符。
  - 列數不等於那一年的天數。
  - 有一列切不出 4 欄。
  - 日期不連續，或不在那一年。
  - 星期對不上。
  - 「是否放假」不是 0 或 2。
- `derived:load`：沒有那一年的日曆快照時，那一天失敗，訊息含 `bin/rails external:office_calendar YEAR=<年>`；快照裡沒有那一天時，訊息指出檔案與日期。兩種情況都不寫入那一天。捷運出入口快照的檢查仍然排在前面。
- 第二個 migration：還有沒帶日型別的路線日時，丟出錯誤，列出路線 Id 與日期，以及要先跑的指令；schema 不變。
- 路線頁：選的那一天沒有資料時，照舊回 200 並列出有資料的日子。

**驗收**：

- `make test` 全綠，包含：
  - 日曆下載的成功案例與每一種失敗。
  - 查一天的平日、假日與備註，以及沒有快照、沒有那一天的情況。
  - `derived:load` 寫入日型別，沒有日曆快照時失敗。
  - `RoutePage::Coverage` 的同類型篩選與另一類的日子。
  - 路線頁的 request 與 component 測試（例子用 10-19 到 10-26）。
  - 首頁卡上的日型別、顯名聲明多的那一行。
- 對真資料：
  - `external:office_calendar YEAR=2026` 寫出 365 天、假日 120 天。
  - 重載後，第二個 migration 能執行。
  - 用開發資料庫裡的平日真資料（15373 的 10-19 到 10-22），請求 `/routes/15373`、`/routes/15373?day=2026-10-22&range=7d` 與 `/`，標示、範圍、首頁卡與 footer 都符合上面跟平日有關的行為。
- 10-26 的驗證不在這個 change 的驗收裡，記在詞彙表「日型別」的待確認（見「用 10-26 的發車數驗證補假日跑的是假日班距」）。
- 對新增與修改的檔案跑 `bin/rubocop`、`bin/brakeman`，沒有 offense，也沒有警告。

**範圍邊界**：

- 在範圍內：日曆快照的下載與查詢、共用下載器、`route_days` 的三個欄位與兩個 migration、loader 寫入、route_day factory 與 21 個 spec 檔的改寫、路線頁範圍與涵蓋日子的顯示、另一類的連結、資料限制那一條、首頁卡上的日型別、顯名聲明那一行、詞彙表與 `docs/data-sources.md`，以及在詞彙表記下 10-26 驗證的待確認。
- 不在範圍內：交件前的 10-26 實測驗證、颱風停班的例外清單、補班與連假的分類、班表對照、30 天與月卡、`bin/health-card`、首頁資料來源那一塊、任何指標定義、其他路線、排程與部署。

## Risks / Trade-offs

- [辦公日曆不等於公車的營運日曆] → 用 10-26 的發車數驗證；交件前做不到，記在詞彙表的待確認，交件後補驗。不符合時另開 change 修正分法；在那之前，10-26 在頁面上被標成假日。
- [日曆年中改版] → 改版的日曆有自己的網址：先把 `DOWNLOAD_URLS` 裡那一年換成新網址再下載，重跑受影響的日子；路線日記下用了哪一份快照。只重跑下載、不換網址，會把舊版存成新日期，`office_calendar_day` 看起來像已經更新。
- [每年的下載網址都不同] → 常數表裡沒有那一年就失敗，訊息列出有的年份；116 年（2027）已經公布，先寫進去。
- [颱風停班照日曆算] → 寫進資料限制；第一次碰到時另開 change，加人工例外清單。
- [7 天裡的假日只有 2 到 3 天，樣本少] → 照用現有「趟數少於 5 標成樣本少」的標示；數字照樣顯示。
- [21 個 spec 檔一起改] → 分三批，每一批都在欄位還可以為空的時候跑綠；改成必填排在最後。
- [第二個 migration 在重載之前就執行] → 它會先檢查，有沒帶類型的日子就停下來，列出要重載的日子與指令。

## Migration Plan

1. 跑第一個 migration（三個可以為空的欄位）。`bin/rails parallel:setup` 會更新測試資料庫。
2. `TURNAROUND_DATA=<資料根目錄> bin/rails external:office_calendar YEAR=2026`。
3. 開發資料庫裡已寫入的日子全部重跑：`bin/rails derived:load ROUTE=15373 FROM=2026-10-19 TO=<最新一個讀檔視窗已結束的日子>`。
4. 跑第二個 migration（改成必填），再 `bin/rails parallel:setup`。
5. 還沒部署的環境（新的資料庫）沒有任何路線日，兩個 migration 直接通過。
6. 回滾：第二個 migration 的 down 把兩欄改回可以為空；第一個的 down 拿掉三欄；頁面程式還原。日曆快照放在資料根目錄，不受回滾影響。
