## Context

路線頁現在是一條路線 `Id` 一頁：`config/route_page.yml` 以 `Id` 為鍵，`RoutesController` 用 `RoutePage.route_ids` 擋 404，`derived:load ROUTE=<Id>` 跑 `analysis/` 的 SQL，`routes` 只取 `GetRoute.gz` 裡 `Id` 等於 `route_id` 的列，`stops` 只取 `GetStop.gz` 裡 `routeId` 等於 `route_id` 的列，事件以 `pathAttributeId` 對回這一條路線、再以 `(route_id, go_back, stop_id)` 對到站序。趟次以 `(bus_id, route_id)` 分割，折返停留以 `bus_id` 配對相鄰兩趟（`analysis/30_layovers.sql` 的 `layover_pairs`），兩趟之間若有不屬於這條路線任何 `pathAttributeId` 的事件經過 3 個以上的站，算「跑了別的路線」。衍生表 `route_day_stops` 一個路線日一套站序，`trips` 記 `path_attribute_id` 不記 `route_id`，`trip_stop_counts.seq` 直接 join `route_day_stops.seq`。

307 在資料裡是兩條路線：16111「307」與 19108「307西藏三民」，各有自己的 `pathAttributeId`（157462、157463；161407、161408）、自己的站序，兩端相同（臺北客運板橋前站(藝文)、莊敬里），中段兩處各繞不同的街。2026-10-24 快照：去程 66 對 65 站、同站位 59 站；返程 62 對 61 站、同站位 55 站；兩條路線的站位在同一個方向內都不重複，共同站在兩邊的先後順序一致。2026-10-22 一天版量到 85 台車裡 55 台兩條都跑，分開算時 307 有 60 組折返配對被判成跑了別的路線，全是去跑 307西藏三民。

使用者 2026-10-23 拍板兩個 `Id` 在路線頁上算一條路線，2026-10-24 選了「主線站序為準，共同站合併」。另一個 session 正在做 `03-route-shape-map`，它改 `derived-tables` 的「Derived export」「Replace one route day atomically」與 `route-page` 的「Stop sequence block」「Data limitations on the page」；這裡對這兩份 spec 只加新的 requirement，不改那幾條。

## Goals / Non-Goals

**Goals:**

- 一個路線頁可以掛好幾個路線 `Id`，趟次、折返停留、來回一趟、週期、行駛時間、換休息試算把它們當一條路線算。
- 沿線載客圖、捷運重疊、站序以頁面路線（設定的鍵）的站序為準，成員的車上人數在共同站位併入。
- `derived:load` 與 `bin/health-card` 用同一組 `Id` 算出同一組數字。
- 307 上線：兩端查證、四個平日載入、數字記下來。

**Non-Goals:**

- 路線圖怎麼畫兩個 `Id` 的路線軌跡：`03-route-shape-map` 的非目標，等它歸檔後另開。
- 把 251 與 251區 用同一個機制合成一頁：`route-251-pages` 決定它們分開，這裡不改。
- 成員路線獨有的站（307西藏三民 的 6 站）在沿線載客圖上畫出來、或畫兩套圖：使用者 2026-10-24 選了不畫。
- `/routes/19108` 轉址到 `/routes/16111`：成員不是頁，回 404，跟其他沒有路線頁的 `Id` 一樣。
- 網址改用路線名稱、Id 那一行以外的頁首改動。
- 自動判斷哪幾個 `Id` 該合成一頁：`member_routes` 是人工設定，跟兩端性質一樣逐路線查證。
- 265區、其他路線、調度站查核分數（`03-depot-inspection-scores`）。
- 兩家業者各自的數字：`routes` 去重後看不出業者，頁面也不分業者。

## Decisions

### 同一頁的附屬路線用 member_routes 設定，頁面與網址只認頁面路線的 Id

`config/route_page.yml` 每條路線的項目多一個選用的鍵 `member_routes`，值是路線 `Id` 的清單；16111 是 `[19108]`。設定的鍵仍是「頁面路線」：`RoutePage.route_ids` 不變，`/routes/16111` 有頁、`/routes/19108` 回 404，首頁一張卡。新的 `RoutePage.member_route_ids(route_id)` 回傳 `[route_id, *member_routes]`，成員出現在別的項目的鍵或清單裡、或成員等於頁面路線本身，都是設定錯誤，載入時與讀設定時都丟 `RoutePage::Ends::InvalidConfiguration` 同一類的錯。

理由：`route-251-pages` 的決定「251區 當成獨立的路線，不跟 251 配對」寫明併計要先定義；這裡的定義是「設定裡掛在一起的就是一條」，跟兩端性質一樣是人工查證的事實，不是從資料推的。替代方案：以名稱前綴自動合併（「307」開頭的都算，否決：307 與 307西藏三民 共用站序的事實要人看過，名稱不保證）；成員也有自己的頁（否決：使用者要的是一條路線一頁，兩頁會有兩套數字）。

### 分析 SQL 吃一組路線 Id：成員各切自己的趟次，折返停留跨成員配對

新變數 `member_route_ids`（DuckDB `INTEGER[]`），`lib/analysis_run.rb` 的 `sql_literal` 多支援 Ruby `Array`（整數陣列寫成 `[16111, 19108]`）；沒給時 SQL 用 `coalesce(getvariable('member_route_ids'), [getvariable('route_id')])`。`routes` 取 `Id` 在清單裡的列（六欄去重，`01-routes-dedupe`），`stops` 取 `routeId` 在清單裡的列並多帶 `stop_location_id`。事件照舊以 `pathAttributeId` 對回它的 `Id`，再對那個 `Id` 的站序，所以趟次仍以 `(bus_id, route_id)` 分割、各用自己的站序判完整；`layover_pairs` 本來就以 `bus_id` 配對 `trips` 裡相鄰兩趟，`trips` 裝了全部成員的趟次之後，跨成員的配對自動成立；`other_route_events` 排除的是 `routes` 裡全部的 `pathAttributeId`，所以成員之間切換不算跑了別的路線。`sequence_check` 的 `route_stop_ids` 子查詢改成只取附屬路線所屬那個 `Id` 的站序；`turnaround_ends` 的 `last_stops`、`route_shape.sql`、`route_day.csv` 的名稱與起迄只取頁面路線。

理由：事件本來就各自掛在附屬路線上，對回自己的 `Id` 是最不動定義的做法；配對與別的路線兩條規則都已經寫成「這條路線的 `pathAttributeId`」，把清單擴大就是把 19108 當成 16111 的附屬路線看待，這正是使用者的決定。替代方案：把 19108 的事件直接改寫成 16111 的站序再切趟次（否決：19108 獨有的站會變成 unknown-stop，趟次的完整性判斷會錯）。

### 沿線的數字以頁面路線的站序為準，成員的車上人數在共同站位併入、獨有站不進

`analysis/40_load_profile.sql` 的 `trip_stop_counts` 多算 `page_seq`：成員趟次的每一站，找頁面路線同一方向、同一個 `stop_location_id` 的站的 `seq`；頁面路線自己的趟次 `page_seq` 就是 `seq`。`load_profile`（卡用）與 `trip_stop_counts.csv`（衍生表用）都以 `page_seq` 當 `seq` 輸出，找不到的列丟掉並計數進品質表。淨上下車（`net_boarding`）照舊在趟次自己的站序上算，不受影響。`mrt_overlap.sql` 對全部成員的站算最近出入口，但重疊度、重疊路段與路段上的車上人數只用頁面路線的站。頁面的 `LoadProfile`、`MrtOverlap`、`LayoverStats` 查 `route_day_stops` 時加 `route_id = 頁面路線`，其餘查詢不變。

理由：對映放在 SQL 這一層，`bin/health-card` 與衍生表吃同一份，`derived-tables` 的「Stored trips match the health card」才成立；放在頁面讀取時算，卡要再寫一套。2026-10-24 快照兩條路線的共同站位在同一方向內都不重複、順序一致，對映是一對一。替代方案：以站名對映（否決：`stopLocationId` 才是站位，站名同名不同位會錯）；成員獨有的站也畫（使用者否決）。

### 衍生表記 route_id 與 stop_location_id，trip_stop_counts 的 seq 是頁面路線的站序

`route_day_stops` 加 `route_id`（integer）與 `stop_location_id`（integer），唯一索引改成 `(route_day_id, route_id, go_back, seq)`；`trips` 加 `route_id`。三個欄位先加成可空、用 `route_days.route_id` 回填 `route_id`、再把兩個 `route_id` 設為必填；`stop_location_id` 留可空，重載之前載入的日子沒有它。`stops.csv` 多 `route_id`、`stop_location_id`，`trips.csv` 多 `route_id`，都接在既有欄位後面；`trip_stop_counts.csv` 欄位不變，`seq` 的意義變成頁面路線的站序。

理由：站序區塊要說成員不停哪幾站，得存成員的站序；資料限制要報每個 `Id` 的趟次，得知道每趟屬於誰。既有的日子不重載也能繼續用：`route_id` 回填後跟以前一樣，`stop_location_id` 只有成員頁才需要。替代方案：成員的站序另開一張表（否決：同一種東西兩張表）；`trip_stop_counts` 同時存自己的 `seq` 與 `page_seq`（否決：頁面沒有任何地方要用成員自己的 `seq`）。

### 頁首、首頁卡與健檢卡的 Id 列出全部路線 Id，用「・」連接

頁首起迄那一行與首頁卡的「路線 Id %{id}」把 `id` 換成 `RoutePage.member_route_ids` 用「・」接起來的字串：「路線 Id 16111・19108」；只有一個 `Id` 的路線一字不變。`bin/health-card` 多 `--also-route ID`（可重複），卡上「路線：」那一行同樣列出全部 `Id`。`data-route-id` 等屬性與網址仍只用頁面路線的 `Id`。

理由：`02-route-stop-sequence` 的決定「路線 Id 加上「路線 Id」標示，放在起迄那一行」把 Id 放在起迄之後，兩個 `Id` 接在同一處最不動版面；「・」是站序區塊已經在用的分隔。替代方案：只寫 16111 再括號補 19108（否決：讀者會以為 19108 是備註）。

### 站序區塊列頁面路線，每個方向一句話說成員不停哪幾站、改停哪幾站

`RoutePage::StopSequence` 讀最新一天 `route_day_stops` 裡頁面路線的站序列出來，另讀同一天每個成員的站序，每個方向在折返那一列之前加一句：「{成員名稱}（路線 Id {成員 Id}）在這個方向不停 {只在頁面路線的站名，照站序}，改停 {只在成員的站名，照站序}。」兩邊站位完全相同的方向不寫這句。成員的名稱取那一天 `routes` 的 `nameZh`，由 `route_day.csv` 帶出、存在 `route_days` 新的一欄 `member_names`（jsonb，`{"19108": "307西藏三民"}`，沒有成員時 `{}`）。

理由：一句話就把差異講完，沿線載客圖不用解釋為什麼少了幾站。替代方案：兩套站序都列（使用者否決）；成員名稱寫死在設定（否決：名稱是快照的事實，路線頁其他地方的名稱都來自 `route_days`）；名稱存進 `route_day_stops` 每一列（否決：同一個名稱重複存幾十次）。

### 資料限制多一段合算說明，附每個 Id 的趟次數

`DataLimitationsComponent` 在有成員的路線頁多一條：「這一頁把路線 Id 16111 與 19108 算成一條路線：趟次、行駛時間、折返停留、來回一趟、週期、換休息試算把兩個 Id 的車合在一起算；沿線載客圖、捷運重疊與站序只用 16111 的站序，19108 在兩條都停的站的車上人數併進去，只有 19108 才停的站不畫。涵蓋的日子裡 16111 X 趟、19108 Y 趟。」數字由 `RoutePage::Summary` 以 `trips.route_id` 分組算，只有一個 `Id` 的路線沒有這一條。

### 307 兩端都停車，查證寫進設定

預期兩端都是 `stop`：2026-10-22 一天版的證據是末站到下一趟起站 0 公尺（臺北客運板橋前站(藝文)）與 34 公尺（莊敬里），兩端折返停留 p50 約 13 到 15 分鐘，板橋前站的靜止點就在站牌上、莊敬里的靜止點在 300 公尺外一處沒有站牌的地方。第一個真資料任務在去重後的資料上照 `route-251-pages` 的做法重驗（GPS 離末站與下一趟起站的距離、靜止最久的時間）；若有一端不是 `stop`，先 `/spectra-ingest` 改 `turnaround-ends` 的情境與這一條，再寫設定。兩端都停車時 `run-time-vs-cycle` 的決定「前段方向由兩端性質決定，去程優先」已經定了來回一趟從去程起站（板橋前站）起算，換休息試算把兩端的折返停留都算進去，頁面摘要列兩端的折返停留，不用新規則。

### TDX 站間旅行時間只做內部對照

新 rake task `external:tdx_s2s_travel_time ROUTE_NAME=307` 用 credentials 裡 `tdx` 底下的憑證（鍵名以 credentials 為準，不寫進 repo）呼叫 `https://tdx.transportdata.tw/api/premium/V3/Map/Estimation/Bus/S2STravelTime/City/Taipei/RouteName/<名稱>`，原始回應存資料根目錄 `external/tdx/<台北日>/S2STravelTime_<名稱>.json`，不進 git、不進衍生表、不釋出。對照方式：同一方向、同一時段，TDX 的站間時間沿 16111 站序加總，跟衍生表算出的分時段行駛時間 p50 擺在一起，差距與可能原因寫在這份 design 的「對照結果」小節。動手前先用瀏覽器讀 TDX 資料使用條款頁（要 JavaScript），確認內部對照可以、外部引用的條件。

理由：TDX 的值是它用近幾個月資料推估的，跟我們的實測是兩種東西，能抓到的是我們趟次切錯或配對漏掉造成的系統性偏差。README 的非目標「依賴拿不到的票證 OD 或 TDX 歷史資料」不受影響：這不是依賴，也不是歷史資料。

### 測試資料：掛在 9001 底下的附屬路線 9050 與 2026-10-23 的成員日

fixture 多一條路線 9050「測試幹線經己站」（`pathAttributeId` 9050，甲站－戊站），站序跟 9001 一樣 10 站，只有丙站換成己站（去程 `Id` 95002、站位 85002，25.0550、121.5010；返程 95007「己站對面」、站位 85007，25.0550、121.5013），其餘站的 `stopLocationId` 跟 9001 相同（81000 到 81009 對應位置）、`Id` 是 95000 到 95009。`static/2026-10-19/` 的三支檔加 9050 的列；新增 `static/2026-10-23/` 是同一份內容。成員日 2026-10-23：新車牌 TEST-0005 先跑 9050 去程（07:00 從 95000 離站，07:12、07:24（己站）、07:36 各到離站，07:50 到 95004），再跑 9001 返程（08:00 從 91005 離站，08:12、08:24、08:36，08:50 到 91009），再跑 9050 去程（09:00 到 09:50，同樣五站）；車上人數：9050 第一趟離站 3、5、7（己站）、6，到站 2；9001 趟 4、6、5、3，到站 1；9050 第二趟 2、4、6（己站）、5，到站 1。`bus_data/2026-10-23/07.jsonl` 放 TEST-0005 07:51 到 07:59 在戊站（25.0600、121.5001）速度 0 的 5 筆；`bus_event/2026-10-24/01.jsonl` 一筆 TEST-0005 的事件讓讀檔視窗結束。test 設定：9001 的項目加 `member_routes: [9050]`。

理由：既有的例子都讀 2026-10-19，成員日放在 2026-10-23 不碰它們；9050 進 2026-10-19 的快照只會讓那一天多 10 列站序（數 `route_day_stops` 的例子要跟著改），事件不變。成員日原本寫 2026-10-20，apply 時（2026-10-24）發現那一天凌晨已經有 fixture 日留下的記錄：TEST-0004 隔天 01 時發車的那一趟（01:05 到 01:50，完整）與 02:10 那筆視窗外的事件，放在 2026-10-20 會多出 2 趟與 1 筆 20.0 分鐘的折返停留，趟次 3、折返停留 2 的數字就不成立；2026-10-23 的讀檔視窗（10-22 22 時到 10-24 02 時）裡只有成員日自己的檔，`cli_spec` 與 `derived_load_command_spec` 用 2026-10-20、2026-10-21 當「沒有檔的日子」的例子也不用改。結束視窗的那一筆放在 `bus_event/2026-10-24/01.jsonl`，是 `RouteID` 0 的非營運記錄，載入時被過濾，不影響任何數字。

## Implementation Contract

- 設定：`shared.routes.<Id>.member_routes`（選用，整數清單）。`RoutePage.member_route_ids(16111)` 是 `[16111, 19108]`，`RoutePage.member_route_ids(10712)` 是 `[10712]`。成員重複出現、成員是另一個鍵、成員等於自己 → `RoutePage::Ends::InvalidConfiguration`，訊息寫出路線與那個 `Id`。
- 網址：`GET /routes/16111` 200；`GET /routes/19108` 404（`public/404.html`）。
- SQL 變數：`member_route_ids` 整數陣列；`AnalysisRun.sql({ member_route_ids: [16111, 19108] })` 印出 `SET VARIABLE member_route_ids = [16111, 19108];`。`derived:load` 一律傳 `RoutePage.member_route_ids(ROUTE)`（沒設定的路線是 `[ROUTE]`）；`bin/health-card --route 9001 --also-route 9050` 傳 `[9001, 9050]`。
- `derived:load ROUTE=19108`：印「19108 是 16111 那一頁的附屬路線，請用 ROUTE=16111」，非零結束，不寫入。成員在那一天的 `GetRoute.gz` 沒有列：那一天失敗，訊息寫出少了哪個 `Id`。

四天 p50 減 TDX：中位數 +3.2 分，範圍 -10.5 到 +38.6，28／39 個時段我們比 TDX 長。離峰（11 到 13 時、18 到 21 時）兩邊差在 5 分鐘以內，去程 06、07 時與兩個方向的 16、17 時我們長 13 到 39 分鐘，22、23 時我們短 5 到 10 分鐘。

可能的原因：

- 時段的對法不同。我們整趟歸起點那個小時，TDX 的 `RunTime` 是每一段在它自己那個小時視窗的值；一趟 307 跑 100 分鐘以上，06 時發的車大半在 07、08 時的路況裡跑，把全部的段都用 06 時視窗加總就偏短。尖峰前的時段差距最大，跟這個解釋一致；要再比就該讓每一段取它預計經過時的視窗。
- TDX 用近 3 個月的平日資料（不含連續假期）產製，是穩定的估計；我們是四個平日（當天那欄只有一天）的 p50，單日的尖峰塞車會直接反映在數字上，16 時那一欄當天 143.9、四天 129.9 就是這樣。
- 我們的行駛時間含每一站的停靠，起站取離站、末站取到站；TDX 的 `RunTime` 是站間旅行時間，每段含不含停靠時間它沒有說。
- 我們漏起站或漏末站的趟次不算，TDX 沒有這個篩選。深夜 22、23 時我們比 TDX 短，趟數少（2 到 22 趟），可能是這個時段的車少停、少等。

沒有看出切趟或配對的系統性錯誤：差距集中在尖峰，方向、量級都跟路況解釋得通，離峰兩邊幾乎一樣。TDX 資料使用條款頁要 JavaScript 才會出現，這次在這裡抓不到內容，沒能確認外部引用的條件；這份對照只放在這裡，頁面、衍生表、釋出檔都沒有用到 TDX 的值，發布前要有人在瀏覽器讀過條款再決定能不能寫到頁面上。

## Risks / Trade-offs

- [成員的站位對不到頁面路線（站位改編號、同名不同位）] → 對不到的列計數進品質表，頁面的資料限制講明「只有 19108 才停的站不畫」；每天載入時數字變大就看得出來。
- [一台車一趟之內切換 `Id`（中途把路線碼切成 307西藏三民）] → 趟次會被切成兩段、各判不完整；真資料驗收任務記下漏起站或末站的比例，跟 2026-10-22 的 26% 比，變多就回頭看切法。
- [去重前的 10-22 數字（569 趟、60 組配對）是估計，去重後會變] → 驗收任務以去重後的數字為準，寫進 design 取代估計。
- [兩端都停車是第一次] → 摘要、試算、來回一趟都已有規則；GPS 查證不符就先改情境。
- [03-route-shape-map 同時在改 `derived_export.sql` 與 loader] → 這裡只加欄位與變數，不動它新加的 `route_shapes`；apply 時先 `/spectra-drift`。
- [TDX 條款讀不到就引用] → 條款讀過才寫進 design，頁面本來就不放。
