# 詞彙表

這份檔案定 TurnAround 的文件、提案、規格與介面文案用哪些詞。程式碼識別字一律英文（`docs/decisions.md` 第 10 條），這裡只對照資料或程式碼裡已經存在的欄位與名稱，不替指標取英文名，那是各 change 的 design 要做的事。

每一條四行：定義、在資料或程式碼裡叫什麼、邊界案例、不要用的說法。邊界案例需要決定時寫「由 change 決定」，這裡不替它決定。

`/spectra-discuss` 會先讀這份檔案。文件或對話用了「不要用」那行裡的說法，或出現這裡沒有的常用概念，就是詞彙漂移，回來改這裡。

整理日期：2026-10-24。核對用的是 2026-10-19 的靜態快照與同一個台北日的事件。2026-10-25 加「班本」與「班表」，改「首頁」，加「分享預覽」。

## 資料來源與檔案

### 動態 feed

- 定義：公運處 blob 上每輛車只保留最新一筆、舊事件約十分鐘後消失的三支：`bus_event` 到離站、`bus_seat_event` 車上人數、`bus_data` GPS。n-gear 每 10 秒抓一次。這是整個系統裡唯一不收就消失的資料。
- 在資料或程式碼裡：`../gems/n-gear` 的 `Feeds`，`kind :dynamic`。`docs/data-sources.md` 表頭寫的「事件型」指同一組。
- 邊界：到離站與車上人數兩支欄位幾乎相同，但分別抓、分別存，不合併。
- 不要用：即時資料、API、事件 feed。

### 靜態 feed

- 定義：路線、站牌、站序、班表、車輛、業者這類一天抓一次就夠的 19 支，每天 04:30 整份複製一次，叫快照。靜態快照之間的差異，就是路線、站牌、班表在哪一天改了。
- 在資料或程式碼裡：`kind :static`，由 `ngear snapshot-static` 抓，存在 `static/<台北日>/<原始檔名>.gz`，同目錄的 `manifest.jsonl` 記 ETag、Last-Modified、sha256。
- 邊界：營運通阻（`GetBusAlertList.gz`）、最新消息這類白天會變的也歸在這組，一天一份，要不要抓得更密由 change 決定。
- 不要用：主檔、基本資料、靜態資料。

### 原始檔

- 定義：n-gear 寫出來、之後不再改的檔案：動態 feed 的小時檔 `<feed>/<台北日>/<HH>.jsonl`（兩小時後壓成 `.jsonl.gz`）與靜態快照。契約是「允許重複、不漏」。
- 在資料或程式碼裡：每一筆是原始 JSON 加上 `_fetched_at`（UTC，ISO 8601）。去重的鍵是 `(BusID, DataTime)`。採集時用滑動窗口擋掉窗口內的重複，壓縮時再去掉同一個小時檔內的重複，跨小時檔的重複則沒有處理，所以下游讀原始檔時一律再去重一次。
- 邊界：同一車同一秒在兩支 feed 各出現一筆不算重複，兩支 feed 分開去重。
- 不要用：資料庫、log、raw data。

### 衍生表

- 定義：每晚批次從原始檔算出來、寫進 PostgreSQL 的表（趟次、折返停留、載客剖面這些）。Rails 只讀衍生表，不碰原始檔。
- 在資料或程式碼裡：`route_days`（一條路線一個台北日一列）、`route_day_stops`、`trips`、`layovers`、`trip_stop_counts`，存逐趟資料、不存彙總，彙總在讀取時用 SQL 算。由 `bin/rails derived:load` 或每晚的 `bin/nightly-load` 寫入（兩者都用 `RouteDayLoader`），先用 DuckDB 跑 `analysis/` 的各個階段與 `analysis/derived_export.sql` 匯出 CSV，再在一個交易裡替換掉一條路線一天的資料。健檢卡仍由 `bin/health-card` 直接讀原始檔，不經過衍生表。
- 邊界：每晚由 Mac mini 的排程（`bin/nightly-load`）算好，直接寫進正式站，一天要等隔天 02:00 讀檔視窗結束才算；手動跑 `derived:load` 時，隔天的 01 時檔出現就能算。逐趟資料含車牌，畫面上不顯示。
- 不要用：報表、cache、統計表。

### 台北日

- 定義：台北時間（UTC+8）的日曆日，00:00 到 24:00。檔案分區與所有分析都用它。
- 在資料或程式碼裡：事件的 `DataTime` 是車機回報的台北時間，沒有時區標記。`_fetched_at` 是抓到的時刻，用 UTC。小時檔是照 `_fetched_at` 換成台北時間之後分區的。
- 邊界：午夜前後抓到的事件，`DataTime` 可能落在前一個台北日，算某一天要連下一天的 `00.jsonl` 一起讀。中山幹線末班 23:00，2026-10-19 的事件裡有 `DataTime` 落在 00 時與 01 時的，就是前一晚發出的趟次。跨午夜的趟次歸哪一天，由 change 決定。
- 不要用：營運日、服務日、UTC 日期。

## 路網物件

### 路線

- 定義：乘客叫得出名字的一條線，例如中山幹線。一條路線一張健檢卡、一個路線頁。
- 在資料或程式碼裡：`GetRoute.gz` 的 `Id` 與 `nameZh`，中山幹線是 15373，`GetStop.gz` 的 `routeId` 填的也是這個。
- 邊界：一條路線在 `GetRoute.gz` 可能有多列，每列一條附屬路線，`Id` 相同、`pathAttributeId` 不同。一個路線頁可以掛在資料裡是獨立路線 `Id` 的附屬路線，由 `config/route_page.yml` 的 `member_routes` 設定，307（16111）掛 307西藏三民（19108）；掛在一起的在網站上算一條路線、一頁，趟次、折返停留、來回一趟、週期、換休息試算合在一起算。畫面上要給路線 Id 時寫成「路線 Id 11764」，放在起迄之後，不接在名稱後面；有成員時列出全部的 Id，用「・」接：「路線 Id 16111・19108」。
- 不要用：線路、公車線、RouteID（事件裡的 `RouteID` 不是路線，見附屬路線）。

### 附屬路線

- 定義：一條路線底下實際跑的一種走法。事件裡每一筆掛的是附屬路線，不是路線。
- 在資料或程式碼裡：`GetRoute.gz` 與 `GetPathDetail.gz` 的 `pathAttributeId`、`pathAttributeName`，事件三支的 `RouteID` 填的就是它。中山幹線有三條：15373「中山幹線」、162347「中山幹線去程半」、162348「中山幹線反程半」。307西藏三民 這種在資料裡自己有路線 `Id`（19108）、自己的站序，網站上卻掛在 307 那一頁底下的，也叫附屬路線；設定裡叫成員（`member_routes`），事件各自對回自己的 `Id` 與站序切趟次。
- 邊界：2026-10-19 的快照裡，162347 的站序正好等於 15373 的整段去程 46 站，162348 正好等於整段返程 45 站。同一天的事件裡 162347 只出現 `GoBack` 0、162348 只出現 `GoBack` 1，跑過這兩條的車同一天也都跑過 15373。它們不是區間車。業者在什麼情況下掛「去程半」「反程半」，還待確認，卡上怎麼併計，由 change 決定。
- 不要用：子路線、路線變體、區間車。

### 區間車

- 定義：只跑路線其中一段的附屬路線，站序是整條路線的一部分，至少有一端不在路線的起迄站。
- 在資料或程式碼裡：仍是一個 `pathAttributeId`，名稱通常帶「區間」。區間車也可能是自己一條路線，像是 251區（路線 `Id` 11764，深坑－公館）在 `GetRoute.gz` 是獨立的一列，有自己的 `Id` 與 `pathAttributeId`，名稱是「251區」，不帶「區間」。
- 邊界：中山幹線目前沒有區間車，「去程半」「反程半」不是區間車，見附屬路線。`docs/background.md` 點名要跑的五條線裡的 251 區間就是 251區。它去程 44 站的站位都在 251（`Id` 10712）的去程上，返程 47 站有 43 站在 251 的返程上，多出來的是公館端折返繞的台電大樓、溫州街口、臺大綜合體育館、臺大四站（2026-10-22 的快照，用 `stopLocationId` 比對）。它算不算這裡定義的區間車、卡上怎麼跟 251 併計，由 change 決定，路線頁上目前是兩條獨立的路線。
- 不要用：短程車、半程車。

### 去返程

- 定義：一條路線的兩個方向。去程是從 `departureZh` 往 `destinationZh`，返程相反。一個趟次只有一個方向。
- 在資料或程式碼裡：`GoBack`，0 去程、1 返程，事件與 `GetStop.gz` 同一套。中山幹線去程是天母往青年公園。
- 邊界：`GetStop.gz` 的 `seqNo` 兩個方向連號，中山幹線去程 0 到 45、返程 46 到 90。`GetPathDetail.gz` 的 `sequenceNo` 也是連號、沒有方向欄，方向要回 `GetStop.gz` 查。
- 不要用：上行、下行，以及單獨出現的往、返。

### 站牌與站位

- 定義：站牌是某條路線某個方向停靠的一個點，站位則是站牌所在的實體位置，多條路線共用。
- 在資料或程式碼裡：站牌是 `GetStop.gz` 的 `Id`，事件的 `StopID` 填的是它，每條路線每個方向各一組。站位是 `GetStop.gz` 的 `stopLocationId`，對到 `GetStopLocation.gz` 的 `id`。
- 邊界：同一路口往返兩側的站牌 `Id` 不同、名稱可能相同。中山幹線兩端都叫「職能發展學院二」，`Id` 分別是 16648（去程起站）與 16738（返程末站）。
- 不要用：站點、車站（那是捷運的）。

### 站序

- 定義：一條路線一個方向的站牌，照 `seqNo` 由小到大排出來的順序。第一站是那個方向的起站，最後一站是末站。站序取自靜態快照，不是量到的；兩份快照的站序不同，就是那一天改了。
- 在資料或程式碼裡：`GetStop.gz` 的 `seqNo`，兩個方向連號（中山幹線去程 0 到 45、返程 46 到 90；251區 去程 0 到 43、返程 44 到 90，2026-10-23 的快照）。衍生表 `route_day_stops` 的 `go_back`、`seq`、`stop_name`，每個路線日一份，取自那一天 `static_day` 的快照。路線頁的站序區塊由 `RoutePage::StopSequence` 讀。
- 邊界：路線頁涵蓋好幾天時，站序取涵蓋日子裡最新的那一天，區塊寫出取自哪一天的快照。有成員的路線頁列頁面路線的站序，每個方向一句話說成員不停哪幾站、改停哪幾站，用站位（`stopLocationId`）比對；衍生表 `route_day_stops` 存每個成員的站序，各帶 `route_id` 與 `stop_location_id`。站序區塊只排順序、不印 `seq`，逐站表照舊印 `seq`，所以同一站在逐站表上是 44 這類號碼。`LoadProfile` 等四個查詢物件在 7 天範圍取到的是最早那天的站序（已知問題，還沒修），修好之前兩處的站名可能不同。
- 不要用：停靠站（分不出是站牌還是站位）、站點順序。

### 起站、末站、折返點、調度站

- 定義：起站是一個方向 `seqNo` 最小的站牌，末站是最大的。折返點是一趟結束、下一趟開始的地方，通常在末站附近，可能是調度站也可能是路邊。每個折返點有一個性質：停車（車停在這裡，等下一趟出發）或直接折返（車在末站讓乘客下車後不停下來等，直接開到下一趟的起站）。折返點位置是這一端車實際停的地方：停車那一端是當天折返停留期間靜止點最密集處，50 公尺內的靜止點以筆數加權的平均；直接折返那一端以末站計。靜止點是折返停留期間同一台車速度為 0 的 GPS 回報落在的座標。靜止格是把靜止回報聚成約 20 公尺（0.0002 度）見方的格子，給地圖畫：路線頁地圖上的方塊就是它，深淺是涵蓋日子合計的筆數，涵蓋比例的分母是 `n_standstill_records`。調度站是業者的營業站，車輛所屬、駕駛報到的地方。
- 在資料或程式碼裡：`GetProvider.gz` 每列是一個業者的一個營業站，`id` 是業者、`stationId` 是營業站。事件的 `StationID` 是車輛所屬的營業站。`GetOrgPathAttribute.gz` 把 `PathAttributeId` 對到 `OrganizationId`，對應關係還待核對。折返點位置沒有任何欄位直接給，由 `analysis/turnaround_facilities.sql` 每晚從 `bus_data` 的靜止點算出，存在 `route_day_ends`（`location_source` 是 `standstill` 或 `end_stop`），旁邊帶三個查核數字：當天結束在這一端的折返停留筆數、其中有靜止回報落在位置 150 公尺內的筆數、位置到末站的距離。靜止格是 `route_day_end_cells`。折返點的性質逐路線查證後寫在 `config/route_page.yml` 每條路線的 `ends`，鍵是結束在那一端的趟次方向 `go_back`，值是 `stop`（停車）或 `pass_through`（直接折返），由 `RoutePage::Ends` 讀，讀頁面時不從資料推。
- 邊界：折返點是不是調度站，決定折返停留裡含不含回場的時間，怎麼判斷由 change 決定。停車那一端是調度站還是路邊，目前還沒區分。中山幹線青年公園端是直接折返，末站馬場町到下一趟起站青年社宅約 200 公尺，2026-10-20 的 75 筆折返停留中位數 1.9 分鐘，GPS 沒有離開這段，這條路線只在職能發展學院二那一端停車。照定義，青年公園端仍然是折返點，只是車不停下來等。直接折返那一端的位置以末站計，不是車停的地方。位置一天量一個，業者改折返方式時會跟著變，路線頁標出用的是哪一天。靜止格只拿來畫，不是位置；一天裡少於 3 台車停過的格子不存，不留任何靠一台車就畫得出來的格子。全路網試跑（`bin/rails survey:end_natures`）用最長靜止判斷每一端，判斷不出來的叫待查證（`undetermined`），理由分樣本太少（`few_layovers`）與介於兩個門檻之間（`between`）；待查證只出現在試跑的報告裡，路線頁仍然只認設定裡人工查證的性質。
- 不要用：總站、終點、場站（單獨出現時分不出是末站、折返點還是調度站），以及不停站（那講的是中途過站不停，不是這件事）、開過去就走（舊的說法，聽起來像過站不停；車其實會在末站讓乘客下車）。

### 路線軌跡

- 定義：臺北市公共運輸處登記的一條路線一個方向行經的線。它是登記的，不是 GPS 量到的。路線頁站序那一塊的路線圖畫的就是它。
- 在資料或程式碼裡：靜態快照的 `GetBusShape.gz`（公車路線軌跡），每列一條 WKT `LINESTRING`，點是經度在前、緯度在後；`RouteID` 對路線 `Id`，`SubRouteID` 是 -1 的兩列（`GoBack` 0、1）是整條路線，`utime` 是公運處的更新時間。衍生表 `route_day_shapes` 每個路線日每個方向一列，`points` 存 `[緯度, 經度]`，由 `analysis/route_shape.sql` 讀進來、`RoutePage::RouteShape` 取出。
- 邊界：`SubRouteID` 不是 -1 的列是特殊附屬路線（例如 10723 的 160559「1狗狗公車」），不算這條路線的軌跡。軌跡會舊：251區 的 `utime` 是 2023-12-29，路線圖下面寫出資料來源與公運處哪一天更新。某一天的快照可能整份缺列（2026-10-23 那份少了 39 列），頁面退回更早有軌跡的日子，但不寫取自哪一天。臨時改道、繞路不會出現在軌跡上；2026-10-22 拿三條路線的 GPS 比過，96% 以上的點落在線 50 公尺內。
- 不要用：路線形狀、shape、行經路線，以及單獨出現的「軌跡」；講車機的 GPS 時寫「GPS 軌跡」。

## 指標

### 趟次與班次

- 定義：趟次是實測的，指同一車牌在同一附屬路線、同一方向，從起站離站到末站到站的一次完整行駛。班次是班表上的，指一次預定的發車，或主管機關核定的每日車次。兩個詞不互換。
- 在資料或程式碼裡：趟次從 `bus_event` 用 `BusID`、`RouteID`、`GoBack`、`StopID`、`CarOnStop`（1 進站、0 離站）、`DataTime` 重建，沒有任何欄位直接標出趟次。`DutyStatus` 實測只有 1 和 2，2 很少，能不能拿來切分趟次還待確認。班次在 `GetTimeTable.gz`（`DepartureTime`、`PathAttributeId`、`DateType`、`DateValue`）與 `GetSemiTimeTable.gz` 的分時段班距，核定的尖離峰班距在 `GetRoute.gz` 的 `peakHeadway`、`offPeakHeadway`。
- 邊界：起站或末站沒有事件（漏站）時趟次算不算完整、跨午夜歸哪一天、同一車連續兩趟掛不同附屬路線怎麼接，由 change 決定。切出來的段至少要觀測到 2 個不同的站才算一趟，只觀測到一個站的段（例如 307 的車上線時在端點站補報的一筆到站）不算，段數寫在健檢卡的資料品質一節。預定班表只涵蓋定時班次，班距型路線的班次數要用班距推。報導裡駕駛說的「一趟」是一個來回：《未來城市》2026-07-31 的報導裡，中山幹線 06:50 發車、09:50 回站是一趟，在這裡是去程與返程兩個趟次。文案要講來回時寫「一個來回」。
- 不要用：行程、車次、班次當趟次用、趟次當班次用。

### 行駛時間

- 定義：一個趟次從起站離站到末站到站經過的時間。按路線、附屬路線、方向、發車小時、日型別彙總，報 p50、p85、p95。
- 在資料或程式碼裡：`trips` 的 `end_time` 減 `start_time`，路線頁由 `RoutePage::RunTimes` 依方向與發車小時彙總。
- 邊界：發車小時用起站離站的那個小時（台北時間）。只算完整趟次。起點取自到站時刻（`start_from_arrival`）或終點取自離站時刻（`end_from_departure`）的完整趟次會排除並計數，因為在起站等發車的時間會被算進去。目前還沒有按附屬路線與日型別分開。
- 不要用：旅行時間、單程時間、車程。

### 來回一趟

- 定義：同一台車從停車端發車、經過另一端、回到停車端，一共花的時間。報導與駕駛口中的「一趟」就是它，等於兩個趟次。
- 在資料或程式碼裡：`RoutePage::Cycles` 從 `trips` 與 `layovers` 算，是前段趟次的起站離站到後段趟次的末站到站。
- 邊界：前段由從停車端發車的方向決定，兩端都停車或都直接折返時是去程，後段是另一個方向。只算兩趟都完整、起點是離站、終點是到站，而且在 `layovers` 裡配得起來的配對，排除的規則跟行駛時間一樣。含另一端的停留：直接折返的那一端只有讓乘客下車、開到下一趟起站的一兩分鐘，兩端都停車的路線則含那一端的休息。
- 不要用：來回、往返一趟、循環、round trip。

### 週期

- 定義：同一台車回到停車端，到下一次回到停車端的間隔，中間經過一個前段趟次，所有停留都算在裡面。這是業者實際維持的節奏。
- 在資料或程式碼裡：`RoutePage::Cycles`，從後段趟次的 `end_time` 到同一台車下一個後段趟次的 `end_time`，兩段相接都要在 `layovers` 裡有配對。
- 邊界：用到站不用發車，因為停車端的離站事件常漏，中山幹線四個平日有三成去程趟次的起點是到站時刻（2026-10-19 到 10-22，量到的）。同一組配對裡，週期等於停車端的折返停留加來回一趟。一台車當天第一個來回沒有週期。週期是車的節奏，雙班制下對不回單一駕駛。
- 不要用：班表時間、排定時間、循環時間、cycle time。

### 折返停留

- 定義：同一車牌本趟末站到站到下一趟起站離站之間的時間。它包含回場、加油、洗車、等發車在內的一切，所以是駕駛休息的上限，不是工時。報 p10、p50、p90，以及不到 15 分鐘的趟次比例。
- 在資料或程式碼裡：同一車牌相鄰兩個趟次的衍生值（`analysis/30_layovers.sql` 的 `layovers`，衍生表 `layovers`）。成立條件是本趟有到末站、下一趟從起站出發、兩趟之間沒有去跑別的路線、差值不為負。另一端漏站不影響，所以只漏起站的趟次可以接在前面，只漏末站的趟次可以接在後面。
- 邊界：量不到的配對（本趟沒有到末站、下一趟不是從起站出發）只計數，因為它們的時間差是拿中途某一站代替端點量的，會比實際長，不能拿來說「其實休很久」。兩趟之間跑了別的路線的配對也只計數，判斷方式是這台車在兩趟之間有 `RouteID` 不是 0、也不是這條路線附屬路線的到離站事件，而且經過至少 3 個不同的站牌（`analysis/params.sql` 的 `other_route_min_stops`）。例如 2026-10-22 中山幹線有一台車返程 11:53 到職能發展學院二，接著去開 206、經過 79 個站，18:01 才從職能發展學院二發下一趟去程。如果不排除，這段會被算成一次 368 分鐘的折返停留。`RouteID` 0 不算別的路線，它是末站勤務結束這類非營運記錄，回場本來就算在折返停留裡。只經過 1、2 個站的也不算，那是在末站把路線碼切成別的路線又切回來，車沒有離開。下一趟掛不同附屬路線（例如 15373 接 162348）算不算同一次折返、當天最後一趟沒有下一趟怎麼算，由 change 決定。雙班制下一台車由兩個人開，這個數字沒辦法對應到某一個駕駛。
- 不要用：layover、recovery time、停留時間（會跟站牌停靠混）、休息時間、緩衝（緩衝是班表上留的，折返停留是實測的）。

### 最長靜止

- 定義：一筆折返停留裡，車連續回報速度 0、而且相鄰兩筆相距 50 公尺內的那一段，從第一筆到最後一筆經過的時間，取最長的一段。
- 在資料或程式碼裡：`layover_evidence.longest_still_minutes`（`analysis/end_nature_evidence.sql`），距離門檻是 `standstill_radius_meters`。
- 邊界：GPS 回報有間隔，一段從第一筆量到最後一筆，會比實際停的時間短，最多短一個回報間隔。沒有回報的折返停留沒有最長靜止；有回報但沒有一筆速度 0 是 0.0。超過 2 分鐘（`nature_still_minutes`）才算停下來過，剛好 2.0 不算。
- 不要用：休息時間、停車時間、待命時間。

### 最遠離站

- 定義：一筆折返停留裡，每一筆 GPS 回報離「本趟末站、下一趟起站」兩站裡較近那一站的直線距離，取最大的那個。
- 在資料或程式碼裡：`layover_evidence.farthest_meters`。
- 邊界：回報有空檔時，車開過的地方可能沒有點，所以會比實際短（251區 公館端兩站相距 616 公尺，最遠離站只到 139 公尺，就是這個原因）。它不進判斷規則，只給人看。
- 不要用：離站距離、偏離距離。

### 班次串

- 定義：同一車牌連續的趟次組成的一串，用來對照汽車運輸業管理規則第 19 條之 2，只要任何連續 4 小時內折返停留累計不到 30 分鐘，就是一條不合規的串。
- 在資料或程式碼裡：趟次與折返停留的衍生值。
- 邊界：名字裡的「班次」其實是實測的趟次，跟「班次對班表、趟次對實測」的區分不一致。`docs/background.md` 要算的指標、`docs/use-cases.md` 第 4 項、`docs/100-days.md` 第 100 天的數字都寫「班次串」，要不要改成「趟次串」還待決定。只用相鄰的完整趟次接成序列，遇到不完整的趟次，或是兩趟之間跑了別的路線，就切斷，因為中間那段的行駛與休息都看不到，不能拿來下結論。4 小時窗怎麼滑、串怎麼切的其他細節，由 change 決定。
- 不要用：連續駕駛（那是對人的，這是對車的）。

### 車上人數

- 定義：某輛車在某站回報的車上乘客數。它是從票證資料推算出來的值，不是真的點人頭，準不準要看乘客下車有沒有刷卡，以及系統怎麼歸零。
- 在資料或程式碼裡：`bus_seat_event` 的 `RemainingNum`，同一筆的 `Level` 是擁擠等級 0、1、2。
- 邊界：每趟會不會歸零、為什麼會跳動，還待確認。要先挑一兩條線實地對照，再用公運處年報的逐路線載客人數，檢查加總起來的量級對不對。
- 不要用：載客量、乘客數、載客人次（年報用語，指刷卡人次，不是同一件事）。

### 載客剖面與淨上下車

- 定義：載客剖面是一個趟次逐站的車上人數曲線，按路線、方向、時段把多趟疊起來，看哪一段長期接近零、哪一段滿載。淨上下車是同一趟相鄰兩站車上人數的差，正值是上車比下車多，它不是上車數，也不是下車數。
- 在資料或程式碼裡：車上人數的衍生值。
- 邊界：漏站時差值會跨站累計。處理原則「尖峰每班次低於 5 人上下車」講的是上下車總數，用淨值對照時要標明是低估。接近零與滿載的門檻，由 change 決定。
- 不要用：運量圖、熱區圖、熱力圖、上下車人次、客流。

### 捷運重疊

- 定義：一條路線有多少站牌靠近捷運。站牌到最近捷運出入口的直線距離在門檻內，就算靠近捷運。一個方向的重疊度是靠近捷運的站牌數除以該方向的站牌數，300、500、800 公尺三種門檻並列，500 公尺是主要的數字。同一方向連續兩站以上都靠近捷運，就算一段重疊路段，要跟它的車上人數一起看。
- 在資料或程式碼裡：`analysis/mrt_overlap.sql` 算出每站最近的出入口與距離，存在 `route_day_stops` 的 `nearest_exit_name`、`nearest_exit_meters`，門檻與重疊路段在 `RoutePage::MrtOverlap`。出入口來自北捷的出入口座標快照，由 `bin/rails external:mrt_exits` 存到資料根目錄的 `external/taipei-mrt-exits/`。
- 邊界：這不是處理原則「與捷運重疊度 70%」的官方算法，官方算法沒有公開，所以畫面只報數字，不標示有沒有超過門檻。靠近捷運不代表可以被捷運取代，像是公車橫越捷運線的時候，路口附近的站也會被算進去。「同一條捷運線的連續段」與「軌跡長度」這兩種定義，要等有捷運路線與站序的資料才能做。
- 不要用：重疊率、捷運覆蓋率、可替代路段。

### 折返點設施

- 定義：每一端的折返點位置附近有什麼，以及這條路線的車從哪些調度站出來、那些調度站在評鑑裡拿幾分。路線頁上每一端有一張地圖，畫靜止格、位置、末站、下一趟起站與公廁（同一地址的公廁一處一個標記）。存的是位置 500 公尺內的每一間；路線頁把同一地址的間併成一處，報 300 公尺內幾處（主數字）、500 公尺內幾處、最近一處是哪一間、幾公尺、那一處有幾間，另列 500 公尺內每一處的清單。兩端之後是調度站那一段：涵蓋日子裡有調度站的最新一天，每個調度站幾台車、幾趟，在查核名單裡的列調度站查核分數，不在名單的與還沒對過的分開寫。只報數字，不判定夠不夠、好不好。
- 在資料或程式碼裡：`route_day_ends` 每條路線每天每一端一列，存位置與查核數字；`route_day_end_toilets` 是位置 500 公尺內的每一間公廁。「間」是公廁快照的一列（環境部全國公廁建檔資料，男廁、女廁、無障礙廁所各一列）；「處」是同一地址的間在讀頁面時由 `RoutePage::Facilities` 併成的，距離取最近的那一間，沒有地址的間各自一處。`route_day_depots` 每個路線日每個調度站一列：`station_id` 是每一趟事件裡出現最多的 `StationID`，業者與營業站名稱對當天的 `GetProvider.gz`，快照沒有這支檔時名稱是空的；`RoutePage::Depots` 取最新一天的列，對 `config/depot_inspections.yml` 分成有分數、不在名單、還沒對三種。路線頁的卡是 `TurnaroundFacilitiesComponent`。
- 邊界：距離都是直線距離，不是走路的距離。資料沒有開放時段，也看不出駕駛能不能借用。大場所的多個地點會併成一處，同一地點登記成不同地址會變成兩處。量不到位置的那一天不列公廁。調度站是車機登記的所屬營業站，不一定是折返點，車在折返停留期間有沒有回調度站量不到。
- 不要用：休息設施、廁所地圖（這裡沒有地圖）、把公廁的間數當處數。

### 調度站查核分數

- 定義：公運處評鑑總體報告書附錄一「臺北市公共運輸處市區公車場站檢查評分表」裡，評鑑時到業者營業站檢查的分數。我們只抄跟駕駛休息有關的八項（調度室環境、休憩室空間及環境、休憩室設施、盥洗室環境、禁菸環境、停車場使用情形、男女專用廁所或性別友善廁所、男女性專用休息室）與總分，照原值抄，兩欄分開。
- 在資料或程式碼裡：`config/depot_inspections.yml` 每一期一個 term（115-1 是 115 年第 1 期），帶報告書的公告頁、下載網址與 sha256、九個項目，以及每個調度站的兩欄分數、檢查日期、附錄頁碼；`not_in_appendix` 是翻過整份附錄、確認不在名單的調度站。業者與營業站要跟 `GetProvider.gz` 的名稱完全相同才算同一站，附錄印的簡稱記在 `printed_as`。由 `RoutePage::DepotInspections` 讀、`RoutePage::Depots` 對 `route_day_depots` 的列。PDF 由 `bin/rails external:pto_assessment TERM=115-1` 存在資料根目錄，不進 repo。
- 邊界：分數是營業站的，不是折返點的。一期一份，下一期公告時人工加一個 term，路線頁用最新的一期。兩欄是報告書印的兩欄，報告書沒有說兩欄是什麼關係，所以不平均、不換算、不評等。名單只有那一期受檢的營業站，不在名單不代表那一站沒有休憩室或盥洗室。
- 不要用：場站評分、評鑑總分（單獨出現時容易跟業者層級的總分混）、休息室評比。

### 漏站

- 定義：趟次的站序上該有卻沒有任何事件的站。10 秒輪詢加上車機回報的間隔，一定會有漏站。漏站率是漏掉的站數除以站序上應有的站數。
- 在資料或程式碼裡：趟次重建時對照 `GetStop.gz` 的站序算出來。
- 邊界：漏到起站或末站會影響趟次是否完整，見趟次與班次。
- 不要用：資料缺失、遺漏。

### 百分位數

- 定義：pN 是把一組數由小到大排，有 N% 落在它以下的那個值，p50 就是中位數。行駛時間用 p85 代表「八成五的趟次跑得完的時間」，折返停留看 p10 代表「最差的一成趟次只停了多久」。不報平均值。
- 在資料或程式碼裡：各指標的衍生值。
- 邊界：樣本少時百分位數不穩，一天的離峰時段一個方向只有幾趟。健檢卡上報的是最近一個月的分佈，一天版的數字只拿來驗證定義。
- 不要用：平均、PR 值。

### 日型別

- 定義：一天屬於平日還是假日，照人事行政總處的辦公日曆來分，「是否放假」是 0 就是平日，2 就是假日。必要時再分出補班日、連假。所有指標都把平日跟假日分開算。
- 在資料或程式碼裡：`route_days.day_type`（`weekday` 或 `holiday`）、`day_note`（日曆的備註，例如「補假」，沒有就是空的）、`office_calendar_day`（用到的那一份日曆快照的日期）。日曆是 data.gov.tw/dataset/14718，由 `bin/rails external:office_calendar YEAR=<年>` 下載，每年的網址不同，寫在 `OfficeCalendarSnapshot::DOWNLOAD_URLS`。下載的檔案存成資料根目錄的 `external/office-calendar/<年>/<台北日>.csv`，`derived:load` 用那一年檔名日期最新的那一份。路線頁的最近 7 天只涵蓋跟選的那一天同類型的日子（`RoutePage::Coverage`）。公運處的資料分不出國定假日。`GetTimeTable.gz` 的 `DateType` 在 2026-10-19 的快照裡全是 0，中山幹線在 `GetSemiTimeTable.gz` 的也是 0。`GetSemiTimeTable.gz` 的 `DateValue` 看起來是星期幾，1 是日、7 是六（2026-10-22 的快照，中山幹線 1 與 7 只有一段 05:30 到 21:00、班距 15 到 20 分鐘，2 到 6 在 06:30 到 08:00 與 16:00 到 17:30 是 4 到 6 分鐘，只在中山幹線上看過）。`GetRoute.gz` 的 `holidayPeakHeadway`、`holidayOffPeakHeadway` 是假日班距。
- 邊界：補假算假日，例如 2026-10-26（一）是光復節的補假。補班日在日曆裡標 0，算平日，2026 與 2027 的日曆都沒有補班日。颱風等天然災害停班不在日曆裡，照日曆算，寫在資料限制裡，第一次碰到時再加人工維護的例外清單。跨午夜的趟次歸發車那一天，所以帶發車那一天的類型。日曆會在年中改版（114 年有一份「(1141020 更新)」），改版的檔案有自己的網址，所以要先把 `OfficeCalendarSnapshot::DOWNLOAD_URLS` 裡那一年換成新網址，再下載、重跑受影響的日子，只重跑下載的話會把舊版存成新的日期。辦公日曆是機關上班的日曆，不是公車的營運日曆。補假日公車是不是跑假日班距，還待確認，因為交件期限（2026-10-24）早於 10-26 的資料，還沒有用真資料驗過。方法是 2026-10-27 02:00 之後載入 15373 的 10-22 到 10-26，數 10-19 到 10-26 每一天、每個方向一整天的趟數，查詢在 day-types 的 design「用 10-26 的發車數驗證補假日跑的是假日班距」（`spectra decisions "10-26"` 找得到）。平日每個方向是 81 到 90 趟（10-19 到 10-22，量到的）。判準是兩個方向的 10-26 都離 10-24、10-25 的平均，比離 10-19 到 10-23 的平均近。如果成立，就在這裡寫下六個數字、拿掉這條待確認。如果不成立，就另開 change 修正分法，在那之前 10-26 在頁面上會被標成假日。
- 不要用：週末（補班的週六不是假日）。

## 交付物

### 健檢卡

- 定義：一條路線一頁，把折返停留、載客剖面、行駛時間、班表達成、捷運重疊與競爭力、折返點設施、門檻對照、建議動作放在一起的定稿文件。底下的數字每晚重算，卡本身每個月底定稿一版供引用。每月的公開報告（月報）是全網彙總，加上各路線的卡。
- 在資料或程式碼裡：目前還沒有。第一張是 Markdown。
- 邊界：「一天版」只拿一個台北日的資料，用來驗證定義，不能引用。月卡要收滿一個月的平日才會出。
- 不要用：dashboard、儀表板、報表、路線頁。

### 路線頁

- 定義：網站上每條路線一頁的畫面，給司機與站長看某一天與最近 7 天的樣子（頁首範圍切換的「當天」「最近 7 天」）。資料由 Mac mini 每晚自動載入（`bin/nightly-load`），一天在隔天 02:00 讀檔視窗結束後的一小時內出現，所以至少晚一天。它不是定稿，所以不是健檢卡。
- 在資料或程式碼裡：Rails 的 `RoutesController#show` 讀衍生表，網址是 `/routes/<路線 Id>`，有路線頁的路線是 `config/route_page.yml` 的 `routes`，目前是 15373 中山幹線、10712 251、11764 251區 與 16111 307（掛 19108 307西藏三民，`/routes/19108` 回 404）。
- 邊界：車牌查詢只能從搜尋進入，不做排行榜，預設都是路線層級的彙總，見 `docs/use-cases.md` 第 11 項。
- 不要用：健檢卡、dashboard。

### 換休息試算

- 定義：給一個動作（縮駛、改區間、離峰改預約、每趟加緩衝），算出車時變化、休息達成率、受影響乘客。三樣交付物的第二樣。資料只看得到車，看不到是誰在開，所以變化用車時與車數表示，不是駕駛的工時。「每趟加緩衝」的輸入是休息、晚到、套用的小時與加在哪一端，休息加晚到是每次折返要留的分鐘數。
- 在資料或程式碼裡：`RoutePage::BufferTrade`，路線頁上的「換休息試算：每趟加緩衝」一塊，網址參數是 `buffer`（休息）、`late`（晚到）、`from` 與 `to`（套用的小時）、`end`（加在哪一端），直接折返那一端的筆數是 `#n_pass_through_layovers`。要留 0 到 40 分鐘每一點的成本曲線在伺服器算好（`#curve`）、寫進回應，拉桿移動時瀏覽器只換成那一點的數字，不重算。
- 邊界：它算的是「這個動作換得多少休息」，不是排班，全網排班最佳化是非目標。目前只有「每趟加緩衝」一個動作，而且只算停車那一端的折返停留。增加的車時給一個區間，下限只把停車那一端不到要留分鐘數的折返停留補足，上限是停車那一端每次折返停留都再加整段要留的分鐘數，不管它本來停了多久。休息達成率是停車那一端量到的折返停留中，不少於休息分鐘數的比例；晚到大於 0 時另報車數不變、再晚到之後還停得到休息分鐘數的比例，兩個都是上限。套用的小時看的是車回到停車那一端（折返停留結束）的台北小時，跟載客剖面的時段（`band`）不是同一件事；加在哪一端只在兩端都停車時能選。直接折返那一端的折返停留不算休息的機會，只報筆數，不算進試算。只用量到的折返停留，不推算其他趟次。縮駛、改區間、離峰改預約與受影響乘客，由之後的 change 決定。班表是另一個東西，見該條：試算算的是量到的折返停留多留幾分鐘要多幾台車，班表是照發車數與停留鋪出來要幾台車，兩個數字定義不同、不必相等。
- 不要用：排班系統、最佳化、班表產生器，以及把套用的小時叫成時段（時段是載客剖面的 `band`）。

### 緩衝

- 定義：班表在停車那一端留給車的時間。換休息試算把它分成兩塊：休息，是駕駛停得到的分鐘數；晚到，是吸收車比量到的再晚回來的分鐘數。兩者相加是每次折返要留的分鐘數。
- 在資料或程式碼裡：休息是網址參數 `buffer`（沿用舊名，0 到 20，預設 15），晚到是 `late`（0 到 20，預設 0），兩者相加是 `RoutePage::BufferTrade#hold`。
- 邊界：緩衝是班表上留的，折返停留是量到的。試算只用量到的折返停留算「每次留這麼多要多花多少車」，不從班表讀緩衝。
- 不要用：recovery time、layover。

### 晚到

- 定義：每次車回到停車那一端，都比量到的再晚的分鐘數。它是一個假設，用來同時看「車數不變的話休息剩多少」與「要保住休息得多花多少車」。
- 在資料或程式碼裡：網址參數 `late`，`RoutePage::BufferTrade#late`；車數不變時的達成率是 `#achieved_share_late`，也就是停留不少於休息加晚到的比例。
- 邊界：它不是誤點，衍生表沒有班表的到站時刻，比不出誤點。量到的那幾天的晚到已經在折返停留裡（車晚到，停留就短），所以晚到只能是「再晚」。晚到比停留還長時，那一次算沒停到休息分鐘數；延到下一趟發車的部分，試算不往下追。
- 不要用：誤點、delay、延誤。

### 班本

- 定義：業界對一台車一天行車單的叫法：這台車當天每個車次幾點發車、起點、預計到達終點、預計返回起點、預計返站時間，由站長或調度員排，駕駛手填職號與姓名。紙本叫行車憑單。
- 在資料或程式碼裡：沒有。開放資料裡沒有任何路線的班本；「業者機動預排班表」（`GetSpecTimeTable.gz`）只有少數路線、只有首站的發車時刻，有路線頁的四條都不在裡面。網站班表頁上一車一張的單子，印出來照它的欄位排版（`TimetableSheetComponent` 的 template）；要手填的六欄（職號、姓名、兩個調度員、兩個里程）在螢幕上不顯示，只在印的時候出現。
- 邊界：班本每天浮動，今天 6 點跑第一班，隔天可能 6:30。雙班制下同一台車兩個人開，仍是一台車一張。「車次」是單子左上角那一格：這台車當天這一班的編號，一張單一個車次；單子上的一列是一個來回，不另外編號。車次不是趟次（趟次是實測的單程），只在講單子時用。
- 不要用：班次當車次用、趟次當車次用。

### 班表

- 定義：網站用量到的行駛時間百分位數、停車端的休息分鐘數與每個方向每小時的發車數，鋪出一條路線一天、每台車一張單子，合起來就是這一天的班表（單一台車那一張是班本）。在瀏覽器裡鋪、改、印，伺服器不存。要不要照著發是調度員的事，網站不替它定位。
- 在資料或程式碼裡：班表頁 `GET /routes/<Id>/timetable`（參數 `day`、`range`、`buffer`、`p` 是起始值），`RoutePage::Timetable` 把量到的資料組成 JSON 嵌進頁面（`script[data-timetable-data]`），量到的值來自 `RoutePage::PlannedRunTimes`、`RoutePage::MeasuredDepartures`、`RoutePage::TimetableOverruns`；鋪排、四小時休息、改時刻、刪列、加列與往後推是 `app/frontend/timetable/` 的 JavaScript（Vitest 測），Alpine 元件 `timetable` 用 `TimetableSheetComponent` 的 template 畫單子。入口是路線頁換休息試算卡的「排成班表」與名稱列的「班表」。
- 邊界：只到單一路線、單一天、車輛：不排駕駛的班（職號、姓名、調度員欄在螢幕上不顯示，印出來留白）、不做全網或多路線、沒有目標函數，所以不是最佳化。預設的發車數是涵蓋日子量到的每小時趟次平均，不讀公佈的班距。四小時休息只報數字、標「若一人開完這張單」，不標合規。改一格發車之後，同一張單後面沒被手動打過的趟次接不上，就往後推到停滿那一端的停留，只往後、不往前，被推過的格子另外標、頁首另外數；手動打的時刻不會被推，比前一趟到達還早時停留印負數；換百分位數、休息或發車數重新鋪排會蓋掉手動改的與被推過的；`buffer` 與 `p` 寫回網址，發車數與手動改的不進網址。沒有 JavaScript 鋪不出來，是網站裡唯一要 JavaScript 的頁。公佈的班表（`GetTimeTable.gz` 這類）在「趟次與班次」那條，不是這裡。
- 不要用：排班系統、最佳化、草稿、試算單、班表產生器。

### 資料限制

- 定義：每份產出都要帶的一段，列出數字的已知限制，像是車不等於人、車上人數看刷卡率、10 秒輪詢會漏站、跨小時檔有重複。
- 在資料或程式碼裡：`docs/spectra/config.yaml` 的 proposal 規則要求牽涉指標定義的提案寫出來。
- 邊界：每張卡、每份月報、每個釋出的檔案都要有，不只是提案。
- 不要用：免責聲明、注意事項。

### 首頁

- 定義：根路徑那一頁，說明這是什麼、交代這個網站從哪篇報導開始、列出有路線頁的路線、各自的最新資料日與那一天每個停車端不到 15 分鐘的比例，再交代資料限制與資料從哪裡來。
- 在資料或程式碼裡：`pages#home`、`HomePage::RouteList`，講起點的區塊是 `OriginStoryComponent`。
- 邊界：有設定但沒資料的路線照樣列出、標成還沒有資料。首頁放且只放一個數字：每張有資料的卡上，每個停車端最新一天折返停留裡不到 15 分鐘的比例與筆數，跟路線頁摘要的重點數字相同；p50、趟次、捷運重疊這些不放。起點區塊引用的報導時刻、日期，以及直接由報導的兩個時刻算出的間隔（「10 分鐘」）不算指標，只出現在起點區塊、跟出處放在一起。
- 不要用：landing page、入口頁、dashboard。

### 顯名聲明

- 定義：政府資料開放授權條款要求的標示，原文在 `docs/data-sources.md`。
- 在資料或程式碼裡：layout 的 `AttributionComponent`。
- 邊界：用網站 layout 的每一頁、每份釋出檔都要有。`public/` 底下的靜態錯誤頁（例如 404 頁）不經過 layout、不顯示資料，不帶。
- 不要用：版權聲明、免責聲明、credits。

### 分享預覽

- 定義：轉貼網址時 LINE、Facebook、Threads 顯示的標題、說明與圖，以及瀏覽器分頁與搜尋結果用的 title。
- 在資料或程式碼裡：layout 的 `<title>`、`meta name="description"`、`og:*`、`twitter:*`。路線頁的字由 `RoutePage::SharePreview` 組，班表頁的標題由 `timetables.show.document_title` 組，首頁與沒有資料的路線頁用 `site.name` 與 `site.description`。
- 邊界：涵蓋到資料的路線頁有自己的標題與說明；班表頁只有自己的標題，說明用站的描述。圖一律是通用的分享圖。說明裡的數字跟摘要的重點數字相同，並帶筆數與「休息的上限」。
- 不要用：OG 卡、社群卡、meta 標籤（單獨出現時分不出是哪一個）。
